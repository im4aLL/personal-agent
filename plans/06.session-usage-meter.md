# 06 - Session usage meter

## Goal

The chat header shows a compact token-usage entry point (coin icon plus formatted count). Clicking it opens a popover with provider-reported input, output, and total tokens for the latest assistant turn in the selected conversation, plus in-memory session totals across every conversation since the app launched. Interrupted turns fall back to the existing characters/4 estimate and are labeled as estimated. Session totals survive conversation switching, reset on reload, and are never written to Turso or `localStorage`. A `Reset session total` action clears the meter without touching conversations or messages. Costs and pricing are out of scope because `ModelInfo` has no pricing data.

## Assumptions and decisions

- **Verified current state.** `src/store/chat-transient.ts` and `chat-transient.types.ts` do not exist yet; plan 01 creates them. `src/hooks/use-chat.ts` owns the `streamText` attempt loop in `streamAssistantResponse`, handles `finish` inside the `for await (const part of stream)` loop, and already has `readPartialOutput`. `src/components/chat/chat-header.tsx` renders only `SidebarTrigger`, the title, a pin button, and `TagEditor`. `formatTokenCount` and `trimTrailingZero` are private helpers in `src/components/chat/message-input.tsx`. `ContextUsageIndicator` also lives in `message-input.tsx`. `src/lib/types/chat.ts`, `src/lib/turso-repository.ts`, and the Turso schema need no change.
- **Provider usage verified in `ai` 7.0.57.** `node_modules/ai/dist/index.d.ts` defines `LanguageModelUsage` with `inputTokens`, `outputTokens`, `totalTokens` and `TextStreamFinishPart.totalUsage`. The SDK emits the `finish` part with `totalUsage` accumulated across every tool-call step. Use `finish.totalUsage`; do not sum `finish-step.usage` again.
- **Prerequisite and ownership.** This plan extends the transient slice created by plan 01 and extended by plan 02. If plan 01 has not landed when implementation starts, create `src/store/chat-transient.ts` and `chat-transient.types.ts` with only the usage fields described here, matching plan 01's structure, and let plan 01 extend the same files later. Do not create a second Zustand store, a `useChatTransientStore`, or a separate transient module.
- **Unit of usage is one assistant turn.** One `streamAssistantResponse` invocation produces one assistant message and at most one usage record. `lastTurnUsage` is keyed by `conversationId` and stores the `messageId` it belongs to. This bounds memory to one record per conversation while preserving the message association. A message-keyed map would grow for every assistant message and need pruning, and the requirement only asks to surface the latest turn.
- **Session totals are app-session-wide and in-memory only.** `sessionTokenUsage` is a single global aggregate across conversations. It survives conversation switching, changes while another conversation is selected, and resets on reload because nothing is persisted. It is never written by `saveMessage`, `saveConversation`, `localStorage`, or config functions.
- **The latest turn is validated against the last assistant message.** The meter renders `lastTurnUsage[conversationId]` only when its `messageId` equals the id of the last assistant message in the selected conversation. This naturally hides stale numbers while a new turn is streaming (the new assistant message id has no record yet) and after regenerate removes the old message.
- **Reset clears session totals only.** The `Reset session total` action clears `sessionTokenUsage` and leaves `lastTurnUsage` intact, because the latest-turn block describes a real message while the session total is the resettable meter. The button is disabled when `turns === 0`. A turn that finishes after a reset is recorded normally into the fresh totals.
- **Deleting a conversation keeps the spend.** Session totals are not decremented. `deleteConversation` clears only that conversation's `lastTurnUsage` entry. If a turn finishes after its conversation was deleted, `recordTurnUsage` still adds to session totals but skips the per-conversation record because the conversation no longer exists.
- **Context usage stays in the composer.** `ContextUsageIndicator` depends on unsent draft text, pending attachments, and slash-activated prompt text owned by `MessageInput`; lifting that state to `ChatArea`/`ChatHeader` just to repeat the same number in a popover is not cheap and would remove the live indicator from where the user is typing. The popover therefore does not duplicate context usage. It includes one muted line pointing to the composer indicator.
- **Accuracy limits are visible in the popover.** Real usage comes from the provider. Fallback estimates use `estimateTokens`/`estimateTextTokens` and are labeled estimated. Retries reset per-attempt usage and only the final attempt is recorded, so failed attempts are undercounted. Title generation, compaction summaries, and plan 04 subagent calls are separate model calls and are not counted. Stopped and failed turns estimate input from the outgoing request and output from visible content and reasoning only, so tool results and intermediate steps in an aborted multi-step turn are not fully represented.
- **Formatting is shared and unchanged.** Move `formatTokenCount` and its private `trimTrailingZero` helper verbatim from `message-input.tsx` to a shared module, preserving behavior exactly: `>= 1_000_000` -> `X.YM`, `>= 1_000` -> `X.Yk`, otherwise the integer, with a trailing `.0` removed. The composer indicator, header badge, and popover all use it.
- **No automated tests.** Project rules say the user tests manually. `npm run lint` (`biome check`) and `npm run build` (`tsc` plus Vite) are the correctness gates. A manual matrix replaces the testing milestone.
- **Coordination.** Plan 01 owns `conversationActivity` and the turn lifecycle; plan 02 owns `messageToolActivity`; plan 03 owns forks; plan 04 owns subagent execution. This plan only adds distinct fields and actions to the same transient slice, does not touch `chat-stream-lifecycle.ts`, and does not alter tool-call handling. Forks use new conversation ids, so a fork shows no latest-turn usage until its first new turn, while session totals are unaffected.
- **No cost display.** `ModelInfo` has no pricing data, so the meter never shows money and does not guess prices.

## Proposed structure

```text
src/lib/
  usage.types.ts                 (new) ProviderTokenUsage, TurnTokenUsage, SessionTokenUsage
  usage.ts                       (new) formatTokenCount, turnUsageFromProvider,
                                       turnUsageFromEstimate, addTurnUsage, EMPTY_SESSION_USAGE
src/hooks/
  chat-usage.ts                  (new) createTurnUsageRecorder: once-per-turn capture and store write
src/store/
  chat-transient.types.ts        (existing from plan 01) extend ChatTransientSlice
  chat-transient.ts              (existing from plan 01) add usage state and actions
  chat.ts                        (existing) clear conversation usage on delete
src/hooks/
  use-chat.ts                    (existing) capture finish.totalUsage per attempt, call recorder
src/components/chat/
  session-usage-meter.tsx        (new) header trigger, popover, rows, reset action
  chat-header.tsx                (existing) render SessionUsageMeter in the right cluster
  chat-area.tsx                  (existing) pass conversationId and lastTurnMessageId
  message-input.tsx              (existing) import formatTokenCount, remove local copies
ARCHITECTURE.md                  (existing) transient slice, capture flow, limits, module list
README.md                        (existing) one feature line
```

Responsibilities:

- `src/lib/usage.types.ts` holds only named contracts. `usage.ts` holds pure arithmetic and formatting with no store or React imports.
- `src/hooks/chat-usage.ts` owns capture policy: one write per turn, provider usage first, estimate fallback, and reading the assistant message for the output estimate. `use-chat.ts` only wires the `finish` part and calls the recorder at each terminal path.
- `src/store/chat-transient.ts` owns state shape and immutable updates only. `chat.ts` gains only a delete cleanup call.
- `src/components/chat/session-usage-meter.tsx` owns presentation and subscribes only to stable references, so typing and streaming do not produce store-driven re-renders.

Data flow:

```text
streamText fullStream "finish" part
  -> part.totalUsage assigned to attemptUsage (reset on each retry attempt)
     -> terminal path calls recordTurnUsage(attemptUsage)
        -> hooks/chat-usage.ts chooses provider usage or estimate
           -> useChatStore.recordTurnUsage(conversationId, turn)
              -> chat-transient.ts: lastTurnUsage[conversationId] + sessionTokenUsage
                 -> SessionUsageMeter selectors
                    -> header badge + popover rows
```

## Milestone 1: Real provider usage and a header entry point

### Outcome

Send a normal prompt: after the turn completes, the chat header shows a coin icon and a formatted count, and opening it shows the session input, output, and total tokens reported by the provider. Sending another turn increases the count. Switching conversations keeps the session total, and reloading returns it to zero. With development builds, the console shows one line per finished turn with the exact numbers and `source=provider`, which can be compared with the popover.

### Implementation

1. `src/lib/usage.types.ts` (new):
   - `ProviderTokenUsage`: `{ inputTokens?: number; outputTokens?: number; totalTokens?: number }`. Structural input for the AI SDK `finish` usage, so `usage.ts` needs no AI SDK type import and no runtime dependency.
   - `TurnTokenUsage`: `{ messageId: string; inputTokens: number; outputTokens: number; totalTokens: number; isEstimated: boolean }`. TSDoc states that `isEstimated` is true only when the whole record came from the estimator, and that missing provider components may be derived arithmetically.
   - `SessionTokenUsage`: `{ turns: number; estimatedTurns: number; inputTokens: number; outputTokens: number; totalTokens: number }`. TSDoc states it is app-session-only and never persisted.
2. `src/lib/usage.ts` (new):
   - Move `formatTokenCount` verbatim from `src/components/chat/message-input.tsx` and document it. Keep `trimTrailingZero` private and documented.
   - `turnUsageFromProvider(messageId, usage): TurnTokenUsage | null`. Returns `null` when all three numbers are missing. Uses `totalTokens` when present, otherwise `input + output`. Derives a missing input or output from the total and the other side, clamped at zero. If only a total is known, keeps input and output at `0` rather than inventing a split. TSDoc records that behavior.
   - `turnUsageFromEstimate(messageId, inputTokens, outputTokens): TurnTokenUsage` with `isEstimated: true` and `totalTokens = inputTokens + outputTokens`.
   - `addTurnUsage(totals, turn): SessionTokenUsage` returning a new object, incrementing `turns`, incrementing `estimatedTurns` only for estimated turns, and summing all three token fields.
   - `EMPTY_SESSION_USAGE` constant with all zeros.
3. `src/store/chat-transient.types.ts` (extend plan 01's file):
   - Import `SessionTokenUsage` and `TurnTokenUsage` with `import type` from `#lib/usage.types`.
   - Extend `ChatTransientSlice` with `lastTurnUsage: Record<string, TurnTokenUsage>`, `sessionTokenUsage: SessionTokenUsage`, and `recordTurnUsage(conversationId: string, usage: TurnTokenUsage): void`.
4. `src/store/chat-transient.ts` (extend plan 01's `createChatTransientSlice`):
   - Initial state: `lastTurnUsage: {}`, `sessionTokenUsage: { ...EMPTY_SESSION_USAGE }`.
   - `recordTurnUsage`: one `set` with a functional updater. Always replace `sessionTokenUsage` with `addTurnUsage(...)`. Write `lastTurnUsage[conversationId]` only when `state.conversations.some((conversation) => conversation.id === conversationId)`; otherwise leave `lastTurnUsage` unchanged. Use the same structural setter type plan 01 introduced. TSDoc states the memory-only contract and the deleted-conversation behavior.
5. `src/hooks/chat-usage.ts` (new):
   - `createTurnUsageRecorder(options: { conversationId: string; messageId: string; estimatedInputTokens: number }): (providerUsage: ProviderTokenUsage | undefined) => void`. TSDoc states it records at most once.
   - The returned closure keeps `let hasRecorded = false`, returns early when already recorded, sets it, converts provider usage with `turnUsageFromProvider`, and calls `useChatStore.getState().recordTurnUsage(options.conversationId, turn)`.
   - In this milestone, when provider usage is missing the recorder logs a development-only line and returns without writing, so no estimated values appear yet.
   - Development-only log: `[personal-agent] turn usage: input=<n> output=<n> total=<n> source=provider conversation=<id>`. Guard with `if (import.meta.env.DEV)`. No logging outside development.
6. `src/hooks/use-chat.ts`:
   - Import `type ProviderTokenUsage` from `#lib/usage.types` and `createTurnUsageRecorder` from `#hooks/chat-usage`.
   - Inside `streamAssistantResponse`, after `const combinedSystemPrompt = ...` and before the `for (let attempt ...)` loop, declare `let attemptUsage: ProviderTokenUsage | undefined;` and `const recordTurnUsage = createTurnUsageRecorder({ conversationId, messageId: assistantMessage.id, estimatedInputTokens: estimateTokens(outgoing.messages) + estimateTextTokens(combinedSystemPrompt ?? "") });`.
   - At the top of each attempt iteration, set `attemptUsage = undefined;` so a retry discards the failed attempt's numbers.
   - In the existing `else if (part.type === "finish")` branch, assign `attemptUsage = part.totalUsage;` next to the existing `finishReason` and `rawFinishReason` assignments. Do not add per-step summation.
   - Success path: immediately after the existing `setMessageStatus(conversationId, assistantMessage.id, "sent")` and `persistConversation(conversationId)` calls, call `recordTurnUsage(attemptUsage);` before title generation.
   - Abort path (`receivedAbort || abortController.signal.aborted`): after the existing status and persist calls, call `recordTurnUsage(attemptUsage);`.
   - `AbortError` catch path: after `setMessageStatus(..., "sent")`, call `recordTurnUsage(attemptUsage);`.
   - Final error path: after the existing partial-output restore and `setMessageError(...)` call, call `recordTurnUsage(attemptUsage);` so a provider error still records provider usage when a `finish` part arrived.
   - Leave the compaction early returns, retry policy, and abort handling otherwise untouched. Do not add a record before the assistant message is added.
7. `src/components/chat/session-usage-meter.tsx` (new):
   - Documented `UsageRow` helper with a local props interface, label on the left in `text-muted-foreground`, value on the right with `tabular-nums`, both `text-xs`.
   - Documented `SessionUsageMeter` component. It selects `sessionTokenUsage` with a selector, and the reset action separately.
   - Render a `Popover` with `PopoverTrigger asChild` around a `Button variant="ghost" size="sm"` containing `<CoinsIcon className="size-3.5" />` and `formatTokenCount(sessionUsage.totalTokens)`. Class it `h-7 gap-1 px-1.5 text-xs tabular-nums text-muted-foreground hover:text-foreground`. Add `aria-label={`Token usage: ${formatTokenCount(sessionUsage.totalTokens)} tokens this session`}`. No tooltip is added because the visible count plus popover is self-describing and avoids stacking a tooltip and popover on one trigger.
   - `PopoverContent align="end" className="w-72"` uses `PopoverHeader`, `PopoverTitle` "Token usage", and `PopoverDescription` "Session only. Nothing is saved." Below it, one section with `Input`, `Output`, and `Total` rows from `sessionUsage`. Keep the content minimal in this milestone.
8. `src/components/chat/chat-header.tsx`: import `SessionUsageMeter` and render `<SessionUsageMeter />` in the existing right-hand `flex shrink-0 items-center gap-1` cluster immediately before the pin button. Do not reorder the pin button or `TagEditor`, and do not change the `ChatHeaderProps` interface in this milestone.
9. `src/components/chat/message-input.tsx`: remove the local `formatTokenCount` and `trimTrailingZero`, import `formatTokenCount` from `#lib/usage`, and leave every call site unchanged.
10. `src/store/chat.ts`: no structural change if plan 01 already composes `createChatTransientSlice(set)`.

## Milestone 3: Honest numbers for interrupted turns

### Outcome

Stopping a turn, failing a turn, or receiving a provider that omits usage still produces a record for the latest assistant message, marked `Estimated`, and adds to session totals and `estimatedTurns`. Deleting a conversation removes its latest-turn record without reducing session totals, and a turn that finishes after deletion still adds to session totals without resurrecting a record for the deleted conversation.

### Implementation

1. `src/hooks/chat-usage.ts`:
   - Replace the missing-usage early return with a fallback: `const turn = providerTurn ?? turnUsageFromEstimate(options.messageId, options.estimatedInputTokens, readEstimatedOutputTokens(options.conversationId, options.messageId));`.
   - Add a documented private `readEstimatedOutputTokens(conversationId, messageId)`: read `useChatStore.getState()`, find the conversation and assistant message, return `estimateTextTokens(message.content) + estimateTextTokens(message.reasoning?.content ?? "")`, and return `0` when the message or conversation is gone. Import `estimateTextTokens` from `#lib/context`.
   - Extend the development log with `source=provider` or `source=estimate` and keep it to one line per finished turn.
2. `src/store/chat-transient.types.ts`: add `clearConversationTurnUsage(conversationId: string): void` to `ChatTransientSlice`.
3. `src/store/chat-transient.ts`: implement `clearConversationTurnUsage` by deleting only that key with an immutability-preserving functional update; return no state change when the key is absent. Document that session totals are intentionally unchanged.
4. `src/store/chat.ts`: in `deleteConversation`, after the existing `set` call and after plan 01's activity cleanup, call `get().clearConversationTurnUsage(id)` so a deleted conversation cannot leave a latest-turn record behind.
5. `src/hooks/use-chat.ts`: no new call sites. Confirm all four terminal paths from Milestone 1 now reach the recorder: success, `receivedAbort` or aborted signal, `AbortError` catch, and the final `lastError` block after partial-output restore.

## Manual testing checklist

1. `npm run lint` and `npm run build` pass with no new warnings.
2. A normal completed turn shows one `turn usage` DEV log line with `source=provider`, and the popover latest-turn values match it.
3. The header badge shows the session total, and two consecutive turns produce a sum equal to the two latest-turn totals.
4. Switching conversations keeps the session total and shows each conversation's own latest turn.
5. A conversation loaded from Turso with no new turns shows no latest-turn record and does not change session totals.
6. Reload the app: badge, session rows, turns, and latest-turn records all reset to zero.
7. Press stop mid-turn: an estimated latest turn appears, `estimatedTurns` increments, and the popover copy explains the estimate.
8. Force a provider error before output: an estimated record with output `0` appears, the error bubble is shown, and session totals increment.
9. Interrupt the network during a long response to trigger a retry, then restore it: only the final successful attempt is counted, and the popover copy explains that failed attempts are not counted.
10. Temporarily force missing provider usage: the record is estimated, the DEV log says `source=estimate`, and the line is restored afterward.
11. Start a turn in conversation A, switch to B, let A finish: the session badge grows while B is selected, and A's latest turn is correct on return.
12. Run two conversations concurrently: session totals equal the sum of both turns, and each conversation shows its own latest turn.
13. Delete conversation A after a turn: session totals do not decrease, and no latest-turn row remains for A.
14. Delete a conversation mid-turn: no console error, no stale latest-turn record for the deleted conversation, and session totals still include the completed spend.
15. Click `Reset session total`: session rows and badge go to zero, turns read `0`, the reset button disables, and the latest-turn block remains.
16. Start a new turn after reset: session totals restart from that single turn.
17. Reset while a turn is in progress: when the turn finishes, it adds to the fresh totals without a duplicate.
18. Regenerate a response: the old latest-turn record disappears as soon as the new assistant message exists, and the new record replaces it on finish; session totals keep both turns' spend.
19. Fork a conversation (plan 03): the fork shows no latest-turn record until its first new turn, and session totals are unchanged.
20. Run a tool-using turn: the provider total includes all steps, and no per-step numbers are shown in the popover.
21. Run a turn with plan 04 subagents enabled: subagent usage is not counted, and the popover copy remains accurate.
22. Confirm the composer context indicator is unchanged after the formatter extraction and that the popover does not repeat its numbers.
23. Confirm no usage is rendered inside any message bubble.
24. Confirm no usage keys appear in `localStorage`, no Turso writes occur, and `Message`/schema files are untouched.
25. Header layout at 360px width and both themes: coin icon, count, pin, and tag editor stay on one line; the title truncates.
26. Keyboard-only: tab to the trigger, open with Enter or Space, tab to the reset button, close with Escape, and confirm the aria-label reads the session total.

## Completion criteria

- A completed turn records provider `finish.totalUsage` once, and the header badge plus popover show a session total that survives conversation switching and resets on reload.
- The popover shows the latest assistant turn for the selected conversation only when its `messageId` matches the last assistant message, and shows session turns, estimated turns, input, output, and total.
- Stopped, failed, and usage-less turns produce an estimated record labeled `Estimated`, with input from the outgoing request and output from visible content and reasoning.
- Retries record only the final attempt, and the UI copy states that failed attempts are undercounted; title generation, compaction summaries, and subagents are documented as excluded.
- `Reset session total` clears session totals only, leaves conversations and messages untouched, and disables at zero turns.
- Session totals keep spend for deleted conversations, while deleted conversations never leave a latest-turn record behind, including late-finishing turns.
- No usage is written to Turso, `localStorage`, config, or `Message`, and no competing store or transient module is created.
- `formatTokenCount` lives in `src/lib/usage.ts` with identical behavior, and both the composer and the meter use it.
- Context usage remains solely in the composer indicator, with the reason documented, and the popover does not duplicate it.
- `ARCHITECTURE.md` and `README.md` describe the meter, its storage, and its limits; every new declaration has TSDoc; `npm run lint` and `npm run build` pass; the manual checklist is completed.

# 03 - Conversation forking

## Goal

From any conversation the user can create a new conversation that is a copy of the history: either the whole conversation (a Fork action in the chat header) or everything up to and including one specific user or assistant message (a per-message "Fork from here" action). The fork is a normal conversation with new ids, new sequential timestamps, copied tags, copied model/thinking metadata, and no pinned flag. It is selected immediately and the app navigates to `/`. Nothing about the source conversation changes, no schema changes, and the only origin marker is the title.

## Assumptions and decisions

- **Title format.** The literal suggestion `${source.title} (forked from ${source.title})` repeats the source verbatim and makes long sidebar titles unreadable, so the fork marker becomes the prefix and the origin is carried verbatim:
  - Whole conversation: `Forked from <source title>`.
  - Message fork: `Forked from <source title> (through message <N>)`, where `N` is the 1-based index of the cut message in the source conversation.
  - Fork of a fork does not stack: `forkTitle` strips a leading `Forked from ` and a trailing ` (through message <n>)` from the source title before rebuilding, so a fork of `Forked from Trip planning (through message 4)` becomes `Forked from Trip planning`, and a message fork of it becomes `Forked from Trip planning (through message 2)`. Accepted edge: a user-renamed title that literally ends in ` (through message 12)` loses that tail when forked.
  - Example: source `Trip planning` -> header fork `Forked from Trip planning`; message fork at the 4th message `Forked from Trip planning (through message 4)`.
  - If a literal suffix is preferred later, switching `forkTitle` to `${base} (forked from ${sourceTitle})` is a localized change.
- **Verified current state.** `src/store/chat.ts` is ~1370 lines and owns `createConversation`, `createMessageId`, `createConversationId`, `loadMessagesForConversation`, `saveConversation` calls. `src/store/chat-helpers.ts` holds pure message transformations. `src/store/chat-transient.ts` does not exist yet (plan 01 creates it). `src/components/chat/chat-header.tsx` currently renders pin + `TagEditor`; `message-bubble.tsx` renders the hover action row last.
- **Plan 01 prerequisite for the busy guard.** The authoritative "this conversation is generating" signal is `useChatStore(state => state.conversationActivity[conversationId])` from plan 01. The guard also treats any loaded message with `status === "streaming"` and `messagesLoading.has(id)` as busy, so the feature is correct even if plan 01 is not landed yet; when plan 01 is absent, ship the message-status + loading check only and add the activity check as one extra condition.
- **Plan 01 and 02 state is structurally impossible to copy.** `conversationActivity` is keyed by source conversation id and `messageToolActivity` by source message id. The fork uses fresh ids for both, so the fork starts with no activity and no tool counts and nothing needs to be stripped. This is asserted in the hardening audit rather than handled in code.
- **Pure transformation lives outside the store.** `src/store/chat-fork.ts` (new) holds `buildForkedConversation` and `forkTitle` with no store import and no persistence. `chat.ts` gains only a thin `forkConversation` action plus the persistence call, which respects the size-review trigger for that oversized file.
- **Id generators move to `src/lib/ids.ts`.** `chat-fork.ts` needs `createConversationId`/`createMessageId`, while `chat.ts` imports `chat-fork.ts`; keeping the generators in `chat.ts` would create an import cycle between the two modules. Moving them and re-exporting from `chat.ts` keeps `use-chat.ts` untouched and keeps generation in `lib` (infrastructure).
- **No new named types, so no sibling `*.types.ts`.** The builder's contract is the existing `Conversation` type plus primitives (`upToMessageId`, `throughIndex`), and the new store action signature is declared on `ChatState`. Every new function and the new hook still get TSDoc.
- **Session-only fidelity.** `saveConversation` (src/lib/turso-repository.ts) persists conversation rows plus `messages` columns only, so in-memory `attachments` and `reasoning` are copied into the fork's live state but, exactly like the source conversation, are gone after reload. `Message` is unchanged, so no accidental persistence is introduced.
- **No automated tests by project rule.** Verification is a manual checklist; `npm run lint` (`biome check`) and `npm run build` (`tsc && vite build`) remain the correctness gates. No migration, no schema version bump, no lineage column.

## Proposed structure

```text
src/lib/
  ids.ts                          (new) createConversationId, createMessageId (moved out of store/chat.ts)
src/store/
  chat-fork.ts                    (new) forkTitle, buildForkedConversation - pure, no store import
  chat.ts                         (existing) re-export ids, add forkConversation action to ChatState
src/hooks/
  use-fork-conversation.ts        (new) busy guard, ensure messages loaded, build, insert, navigate
src/components/chat/
  chat-header.tsx                 (existing) Fork button (GitForkIcon, tooltip, aria-label)
  chat-area.tsx                   (existing) instantiate the hook, pass handlers
  message-list.tsx                (existing) pass onForkFromMessage down
  message-bubble.tsx              (existing) "Fork from here" action
ARCHITECTURE.md, README.md        (existing) docs
```

Responsibilities:

- `src/lib/ids.ts` - two documented one-line factories, `conv-<ts>-<rand>` / `msg-<ts>-<rand>`, unchanged format so nothing downstream notices the move.
- `src/store/chat-fork.ts` - pure copy semantics: cut point, new ids, sequential timestamps, transient-field stripping, tags/pin/title rules, summary remap. No `useChatStore`, no repository import.
- `src/store/chat.ts` - `forkConversation(sourceId, upToMessageId?)` inserts the fork at the head of `conversations`, prepends its summary to `today`, marks it loaded, selects it, and fires `saveConversation` when Turso is configured. It never mutates the source.
- `src/hooks/use-fork-conversation.ts` - the only place that knows about "load first, then fork, then navigate", the busy guard, and the toasts.
- `chat-area.tsx` - single hook instance; both UI entry points receive handlers as props, matching the existing `onEdit`/`onRegenerate` wiring.

Data flow:

```text
ChatHeader Fork / MessageBubble "Fork from here"
  -> useForkConversation (guard: activity | streaming message | messagesLoading)
     -> loadMessagesForConversation(sourceId) when not loaded
        -> chat.ts forkConversation(sourceId, upToMessageId?)
           -> chat-fork.ts buildForkedConversation(source, upToMessageId) -> Conversation | null
              -> store insert + select + today summary
                 -> saveConversation(fork) when Turso configured
                    -> navigate("/")
```

## Milestone 1: Whole-conversation fork from the chat header

### Outcome

Open any conversation with messages, click the new GitFork button in the header, and the app immediately lands on a new conversation titled `Forked from <source title>` containing every message in order. The fork appears at the top of the Today group in the sidebar, is selected, and the source conversation is unchanged. Reloading (with Turso configured) shows the fork and its messages again. The Fork button is disabled while the source is generating, while its messages are still loading, or when the conversation has no messages.

### Implementation

1. `src/lib/ids.ts` (new): move `createConversationId` and `createMessageId` verbatim from `src/store/chat.ts` (lines ~329-335) with TSDoc ("opaque unique id, `<prefix>-<epoch ms>-<random>`") and remove the local definitions from `chat.ts`. In `chat.ts` add `export { createConversationId, createMessageId } from "#lib/ids";` so `use-chat.ts` and the existing imports keep working.
2. `src/store/chat-fork.ts` (new):
   - `export function forkTitle(sourceTitle: string, throughIndex?: number | null): string` - documented; strips the leading `Forked from ` prefix and a trailing ` (through message <n>)` from `sourceTitle`, then returns `Forked from <base>` plus ` (through message ${throughIndex + 1})` when `throughIndex` is a number. Falls back to `Forked from New chat` semantics naturally because the base is whatever the source title is.
   - `export function buildForkedConversation(source: Conversation, upToMessageId?: string | null): Conversation | null` - documented, returns `null` when there is nothing to copy. Rules:
     - Cut index: `upToMessageId == null` -> `source.messages.length - 1`; otherwise `findIndex`; `-1` returns `null`.
     - `messages.length === 0` returns `null` (never fork an empty conversation).
     - Copy `source.messages.slice(0, cutIndex + 1)` in order, each mapped to `{ ...message, id: createMessageId(), createdAt: new Date(base + index) }` with `base = Date.now()` captured once, dropping `status` and `error` by omission (destructure them out so they cannot leak), keeping `role`, `content`, `reasoning`, `editedAt`, `model`, `thinkingLevel`, `attachments`.
     - Conversation: `id: createConversationId()`, `title: forkTitle(source.title, upToMessageId == null ? null : cutIndex)`, `pinned: false`, `tags: [...source.tags]`, `summary: null`, `summarizedUpToId: null` (summary carry-over is Milestone 3), `createdAt: now`, `updatedAt: now`.
   - No store or repository import in this module; no `.types.ts` sibling because no new named contract is introduced.
3. `src/store/chat.ts`:
   - Import `buildForkedConversation` from `./chat-fork`.
   - Add to `ChatState`: `forkConversation: (sourceId: string, upToMessageId?: string | null) => string | null;` with TSDoc describing the contract (returns the new id, or `null` when the source is unknown, unloaded, or has nothing to copy).
   - Implement inside `useChatStore` right after `createConversation`, ~25 lines: read `get()`, find the source by `sourceId`, return `null` unless `loadedConversationIds.has(sourceId)` (messages must be loaded - the hook guarantees this), call `buildForkedConversation`, return `null` when it yields `null`, then `set` `conversations: [forked, ...state.conversations]`, `selectedConversationId: forked.id`, `loadedConversationIds` with the new id added, and `today: [forkedSummary, ...state.today]` where `forkedSummary` is the fork without `messages`/`summary`/`summarizedUpToId`. Finally `if (isTursoConfigured()) { void saveConversation(forked); }` and return `forked.id`. Because the fork carries `summary` and `summarizedUpToId` keys, `saveConversation` takes the summary-aware `INSERT` branch and writes the conversation row plus all message rows in one batched call.
4. `src/hooks/use-fork-conversation.ts` (new):
   - Local documented helper `isConversationBusy(state, conversationId, messages)`: `true` when `state.conversationActivity[conversationId]` is set (plan 01), or `state.messagesLoading.has(conversationId)`, or the loaded messages contain one with `status === "streaming"`.
   - `export function useForkConversation(): { forkConversation: () => Promise<void>; forkFromMessage: (messageId: string) => Promise<void>; canFork: boolean }` (documented). Internals: `useChatStore(selectSelectedConversation)` for the current source, a `conversationActivity` selector for the busy state, `useRef(false)` in-flight flag (guards double clicks before React re-renders the disabled buttons), `useNavigate`, and `toast`.
   - Shared async core `runFork(upToMessageId?: string)`: no-op when the in-flight ref is set; read `useChatStore.getState()`; `const source = selectSelectedConversation(state)`; return silently when there is no source; when busy, `toast.error("Wait for the current response to finish")` and return; set the ref; `try` { if `!state.loadedConversationIds.has(source.id)` `await loadMessagesForConversation(source.id)`; call `state.forkConversation(source.id, upToMessageId ?? null)` (re-reading state after the await); on `null` `toast.error("Nothing to fork yet", { description: "This conversation has no messages to copy." })`; on success `navigate("/")` and `toast.success("Conversation forked")` } `finally` { clear the ref }.
   - `canFork`: `Boolean(source) && !isForking && !isBusy && (notLoaded || source.messages.length > 0)`.
   - Returning untyped object literals follows `useChat()`; no new `.types.ts`.
5. `src/components/chat/chat-header.tsx`: extend `ChatHeaderProps` with `onFork: () => void; forkDisabled?: boolean`. Import `GitForkIcon` from `lucide-react`. In the right-hand `flex shrink-0 items-center gap-1` cluster, add the fork `Tooltip` + `Button variant="ghost" size="icon-xs"` (`aria-label="Fork conversation"`, `disabled={forkDisabled}`, `<GitForkIcon className="size-3.5" />`, `<TooltipContent>Fork conversation</TooltipContent>`) as the first child, before the pin button, so conversation-level actions stay grouped and the wider `TagEditor` stays last. Do not change the title element (`min-w-0 truncate flex-1`) or the cluster's `shrink-0`.
6. `src/components/chat/chat-area.tsx`: `const { forkConversation, canFork } = useForkConversation();` and pass `onFork={forkConversation} forkDisabled={!canFork}` to `ChatHeader`. Nothing else changes in this milestone.

## Milestone 3: Carry the compaction summary into the fork

### Outcome

Forking a conversation that already has a valid compaction summary keeps the compressed context instead of silently re-sending the full history. When the fork copies through the summarized cutoff message, the summary text is carried over and `summarizedUpToId` is remapped to the fork's own message id. When a message fork stops before the cutoff, the summary is dropped rather than lying about content the fork does not contain.

### Implementation

1. `src/store/chat-fork.ts`, inside `buildForkedConversation`, replace the hardcoded `summary: null, summarizedUpToId: null` with a documented rule:
   - `const cutoffIndex = source.summarizedUpToId ? copiedSourceMessages.findIndex((message) => message.id === source.summarizedUpToId) : -1;` computed on the source slice before ids are assigned.
   - Valid summary requires `typeof source.summary === "string" && source.summary.trim().length > 0 && cutoffIndex !== -1 && cutoffIndex <= cutIndex`.
   - When valid: `summary: source.summary`, `summarizedUpToId: forkedMessages[cutoffIndex].id` (the already-generated new id). Otherwise both stay `null`.
   - Add a short comment that the copied messages `[0..cutoffIndex]` are byte-identical to the source, which is exactly what the summary still describes, so `isSummaryInvalidatedBy` (src/store/chat-helpers.ts) keeps working on the fork with no changes.
2. No change is needed in `saveConversation`, `loadConversationMetadata`, or `buildOutgoingContext`: the fork's `summary`/`summarizedUpToId` keys are persisted by the summary-aware branch of `saveConversation` already used by `setConversationSummary`.
3. Keep the whole-fork path (`upToMessageId == null`) relying on the same rule: the cutoff is always inside the copied range, so a whole fork always carries a valid summary when the source had one.

### Verification

1. `npm run lint` and `npm run build` pass.
2. Build a conversation long enough to auto-compact or press the manual Compact button, then confirm the DEV console logs `context usage: ... + summary` on the next send.
3. Fork it from the header, open the fork, and send a short message: the DEV console log for the fork must also include `+ summary` with a similar token estimate (not the full-history estimate). This proves the summary survived the copy and is applied.
4. Reload, reopen the fork, send again: the DEV log still shows `+ summary` (the remapped `summarized_up_to_id` was persisted).
5. Message fork before the cutoff: fork from a message that sits inside the summarized region. The DEV log for that fork must not contain `+ summary`, and the request sends the raw copied history.
6. Message fork after the cutoff: fork from a message after the cutoff. The DEV log shows `+ summary`, and the first two messages still render normally in the fork.
7. Invariant check: in the fork created in step 3, edit the first user message. `isSummaryInvalidatedBy` must clear the summary (the DEV log stops showing `+ summary` on the next send), proving the remapped cutoff id is a real id inside the fork.

### Deliberately deferred

- Re-generating a summary for the fork when the cut drops it (the fork simply compacts again naturally on a long enough turn).
- Preserving the source's summary when a message fork cuts the summarized region in half (impossible without re-summarizing).
- Any manual "reset summary" control.

## Manual verification checklist

Project rule: the user tests manually, so no unit, integration, or E2E tests are added and no test harness is introduced. The substitute is the manual matrix below, run in order after every milestone's own verification steps, plus `npm run lint` and `npm run build` as gates.

1. `npm run lint` and `npm run build` pass with no new warnings.
2. Whole-conversation fork from the header creates a new conversation titled `Forked from <source title>` with every message in order, selected, on `/`.
3. Message fork from an assistant message copies the prefix through that message and titles it `Forked from <source title> (through message N)`.
4. Message fork from a user message ends with that user message and an empty composer.
5. No fork icon on error bubbles; no error banner, spinner, tool-call count, or sidebar spinner appears in a fresh fork.
6. Fork preserves role, content, model metadata, thinking level, reasoning block, and in-memory attachments; after reload the text and metadata persist while attachments/reasoning behave exactly like the source conversation.
7. Fork copies tags and is unpinned; the source conversation keeps its own tags and pin and is otherwise unchanged (messages, title, `updatedAt`).
8. Fork is disabled while the source is generating (including during compaction), while messages are loading, and for an empty conversation; an idle conversation can still be forked while another one streams.
9. Rapid double-click produces exactly one fork.
10. Message ids in the fork are all new; timestamps are strictly increasing; after reload message order is identical.
11. Compaction: whole fork of a compacted conversation keeps the summary (DEV log shows `+ summary`); fork cut before the cutoff drops it; fork cut after the cutoff keeps it; editing inside the fork invalidates it through the existing helper.
12. Forks of forks do not stack titles: a fork of `Forked from Trip planning (through message 4)` reads `Forked from Trip planning`.
13. Narrow window (~360px) and both themes: header cluster stays on one line, message action row fits, tooltips readable, focus ring visible on both fork buttons and keyboard focus reveals the action row.
14. Without Turso configured, forking works in memory for the session and nothing is written to `localStorage`.

## Completion criteria

- A fork can be created for a whole conversation and for any user or assistant message, from visible header and hover actions, with tooltips and accessible labels.
- The fork has new conversation and message ids, strictly increasing timestamps, copied tags, no pin, no streaming/error/turn-activity/tool-activity state, and the exact titles `Forked from <source>` / `Forked from <source> (through message N)` with no prefix stacking.
- Compaction summaries are carried only when the copy covers their cutoff, with `summarizedUpToId` remapped to the fork's message id.
- Forking is blocked while the source is generating or loading and never produces an empty fork; it selects the fork and navigates to `/`.
- No schema change, no migration, no lineage column, and no writes to the source conversation; `Message`, `saveConversation`, and the repository layer are untouched.
- `ARCHITECTURE.md` and `README.md` describe the feature and the new modules; every new declaration carries TSDoc.
- `npm run lint` and `npm run build` pass and the manual checklist is completed by the user.

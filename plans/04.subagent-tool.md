# 04 - Subagent tool (spawnSubagent)

## Goal

The parent model can call one tool, `spawnSubagent`, to hand a self-contained research or drafting task to a nested model call that uses the same provider and model as the current conversation. The parent waits for the result and answers normally; the subagent returns a small, cited text report that the parent folds into its reply.

Every subagent run requires explicit user approval. The application never spawns a subagent silently: a model-initiated spawn opens an approval dialog showing the exact task, model, and conversation, and nothing runs until the user clicks Approve. Denying returns an error-shaped tool result and the parent answers without the delegation. The only bypass is an explicit per-turn `Allow subagents` control that the user turns on before sending; natural-language requests from the model or the prompt are not treated as approval.

Calls are bounded: at most 5 subagents per parent turn, at most 5 running at once across the app, one nesting level only, a 120 second timeout, a 150k token allowance for the subagent's own run, and a ~2k token report returned to the parent. There is no child conversation, no transcript viewer, and no new persisted state.

## Assumptions and decisions

- **150k interpretation (flagged as an open decision).** `SUBAGENT_TOKEN_BUDGET = 150_000` is the subagent's own allowance of estimated input + output tokens across its entire nested run (system prompt + task + tool results + every step's completion), **not** the size of the report returned to the parent. A 150k-token tool result would overflow the parent context, so the report is capped separately at `SUBAGENT_RESULT_TOKEN_CAP = 2_000` tokens (about 8,000 characters, measured with the existing `estimateTextTokens` from `src/lib/context.ts`). Confirm this reading. If 150k was meant as an aggregate across all 5 subagents in a turn (up to 750k spend per turn), the budget needs a shared per-turn counter instead of a per-run stop condition; this plan does not build that.
- **Budget enforcement is per completed step.** The nested `generateText` gets a custom `stopWhen` that stops when cumulative `step.usage.totalTokens` reaches the budget. That bounds the loop but lets a single step overshoot by its own output, which is inherently capped by the model. The alternative is a hard `maxOutputTokens`, which would also truncate reasoning; this plan prefers the step-based check and records the tradeoff.
- **Approval is mandatory, per spawn call.** `spawnSubagent` is registered whenever the parent tool set is built for a non-Gemini provider, so the model can propose delegation, but `execute` first calls `requestSubagentApproval({ conversationId, conversationTitle, task, providerName, modelName, signal })` and awaits a user decision. Approval is required for every spawn call. The dialog shows the exact task string as plain text, the current conversation title, and the inherited provider/model; the user can Approve or Deny. Denying returns `{ error: "Subagent request denied by the user." }` and the parent turn continues. Closing or pressing Escape on the dialog counts as Deny. Deny is the initially focused action, so pressing Enter cannot accidentally approve. There is no Settings switch that silently enables spawning.
- **Explicit per-turn opt-in is the only bypass.** A small `Allow subagents` control in the composer, shown only when the active provider supports tools, sets a one-shot flag for the next send. When it is on, `createSubagentTool` skips the dialog for calls in that turn, still subject to all limits. The flag is captured when the message is sent and resets after the turn; it is never persisted, never model-controlled, and never derived from prompt text. If plan 05 lands, `QueuedMessage` must carry this flag so a queued item keeps the approval the user gave when writing it. Regenerate, edit, and retry start a new turn with the flag off, so they prompt again.
- **Approval queue, not parallel dialogs.** The AI SDK can execute several tool calls in parallel, so several spawn requests can arrive at once. A module-level FIFO queue holds pending requests and exposes only the first one; the dialog shows one request at a time. Approving or denying reveals the next. Each request has its own resolver and is resolved exactly once. Stopping the parent turn, deleting the conversation, or a parent abort cancels every pending request for that turn and closes the dialog.
- **Read-only research subset.** Subagents get `fetchUrl` and `webSearch` only, and only when the matching Settings > Tool toggles are on plus a saved Tavily key for `webSearch`. Explicitly excluded: `spawnSubagent` (depth), `googleSearch` and `duckduckgoSearch` (they open human-in-the-loop windows and must never be launched from a background nested turn), `createPdf` (writes a file), `remember` (writes to Turso), and `recall` (reads stored personal memory without the parent's intent and would leak it into a report).
- **`recall` decision:** excluded now. It is read-only, but memory retrieval is a parent-level, user-visible behavior; a subagent report would carry memory content the parent never asked to surface. Revisit only with an explicit requirement.
- **Model inheritance is dynamic.** The tool reads provider, model, and thinking level from `useChatStore.getState()` at execution time through a getter, so a model change mid-turn applies. `generateText` is not given the parent's conversation history or summary, only the parent's system prompt plus the subagent instruction.
- **Thinking level is inherited** (`resolveReasoningEffort(thinkingLevel)`), matching the parent request. Flagged as a reversible decision; forcing `"none"` would be cheaper and faster but inconsistent.
- **Per-turn cap vs concurrency.** `SUBAGENT_MAX_PER_TURN = 5` is used twice: a per-tool-instance cumulative counter (the tool instance is created once per parent attempt, so retries reset it) and a module-level in-flight limiter across all parents. Both are needed: the cumulative counter stops a long turn from spawning 5 at every one of its 8 steps; the in-flight limiter stops two conversations from multiplying cost.
- **Abort and timeout.** The AI SDK passes the parent's `abortSignal` into `tool.execute`, which is the parent attempt/turn controller. That signal is forwarded to the nested `generateText`. A local `AbortController` adds the 120 second timeout and forwards the parent abort; `AbortSignal.any` is avoided because `tsconfig` targets ES2020 and older WKWebView builds lack it.
- **Never throws.** The tool returns `{ report, truncated? }` on success and `{ error }` on every failure, matching existing tools such as `fetchUrl` and `webSearch`. Zod validation failures are handled by the SDK itself and surface as tool errors, not thrown exceptions into the parent stream.
- **Approval state is in-memory and has one owner.** `src/lib/subagent-approval.ts` owns a module-level queue, the active request, and the resolvers. `src/hooks/use-subagent-approval.ts` exposes it to React through `useSyncExternalStore`. This avoids adding approval functions or resolvers to Zustand and keeps the queue usable from `tool.execute`, which is plain TypeScript. Nothing about a pending approval is written to Turso or `localStorage`; a reload drops it and the parent stream is gone as well.
- **Approval UI is app-wide.** The dialog is mounted once in `src/components/layout.tsx`, not inside `ChatArea`, so a request stays visible if the user switches conversations or opens Settings while the parent turn is still running. It names the source conversation so a background request is unambiguous.
- **Coordination, not code dependency.** `plans/01.conversation-activity-indicator.md` owns the per-turn `AbortController` and sidebar spinner. `plans/02.tool-call-count.md` owns the transient tool row. Neither is required for the delegation itself to work; without plan 02 the call is invisible in the UI, and without plan 01 the tool still receives the attempt-level signal. **Plan 04 adds no persisted state and no Zustand slice.** It must not create `useSubagentStore`. The approval queue is a module-level registry, not a second store.
- **Naming.** "Subagent" here is an internal delegated worker, unrelated to `useAgentsStore.customAgents` (persona presets). The plan keeps both names distinct to avoid confusion.
- **No automated tests** per project instructions. Verification is manual; `npm run lint` (`biome check`) and `npm run build` (`tsc` + vite) are the correctness gates.

Responsibilities:

- `chat-model.ts` owns the one way the app turns a stored provider into an AI SDK model. `title.ts`, `use-chat.ts`, and `subagent.ts` all use it, so proxy/header behavior cannot drift.
- `tools/research.ts` owns the definition of the safe read-only subset. It is the single source of truth for what a subagent may call, and it deliberately never includes interactive or side-effecting tools.
- `subagent-approval.ts` owns consent. It knows nothing about models or tools: it accepts a request, queues it, returns a promise, and resolves it once with `approved`, `denied`, or `cancelled`. It also handles the parent abort signal and is the only code allowed to mark a request approved.
- `use-subagent-approval.ts` adapts the queue to React without copying state into a store.
- `subagent-approval-dialog.tsx` renders the active request as untrusted plain text and resolves it. It has no knowledge of how the subagent runs.
- `lib/subagent.ts` owns one nested run: prompt composition, budget stop condition, timeout, parent abort, report truncation. It holds no counters, so it stays stateless.
- `tools/subagent.ts` owns the AI SDK tool contract and admission control (approval gate, per-turn counter, in-flight limiter, depth guard, error shaping).
- `tools/registry.ts` owns parent tool assembly only. Dependency direction is `registry -> tools/subagent -> subagent-approval + lib/subagent -> tools/research -> tool factories`, with no cycles and no import of `#hooks/*` or `#store/*`.

## Milestone 1: Extraction and approval-gated delegation

### Outcome

With URL fetching enabled, sending `Delegate to a subagent: fetch https://example.com and report its title and the first heading` makes the model call `spawnSubagent`. Before anything runs, an approval dialog appears in the app with the exact task, the source conversation, and the inherited provider/model. Clicking Deny closes the dialog, the parent receives a `denied` tool result, and the parent still answers without delegating. Repeating the turn and clicking Approve runs the nested call on the same provider and model, and the parent's answer contains the delegated facts. The parent tool row (plan 02) shows `spawnSubagent` running and then done. Existing direct tool calls behave exactly as before, proving the registry extraction is behavior-preserving.

## Milestone 2: Explicit per-turn opt-in

### Outcome

The composer shows an `Allow subagents` toggle whenever the active provider supports tools. With the toggle off, every model-initiated `spawnSubagent` call opens the approval dialog. With the toggle on, the next message's subagent calls run without a dialog, still subject to every limit. The toggle resets immediately after the message is sent, so the following turn prompts again unless the user turns it on again. Turning it on is the only way to skip the dialog; typing "use a subagent" in the prompt is not treated as approval.

## Milestone 3: Admission control and parallel safety

### Outcome

A turn can start at most 5 subagents total, at most 5 run at once across the whole app, a 6th attempt returns an actionable error result instead of blocking or throwing, and no aborted, timed-out, or failed run can leak a slot permanently. Multiple spawn requests emitted in parallel produce approval dialogs one at a time, in request order, and denying one request does not cancel the others.

### Implementation

1. `src/lib/tools/subagent.ts`:
   - Add a per-tool-instance counter `let spawnedThisTurn = 0;` inside `createSubagentTool`. In `execute`, after the depth guard: if `spawnedThisTurn >= SUBAGENT_MAX_PER_TURN`, return `{ error: "Subagent limit reached: this turn already used its 5 subagents..." }`. Increment only after a slot is acquired, so rejected calls do not consume the quota. Never decrement: it is a cumulative per-turn budget.
   - Add module-level limiter state and documented helpers `tryAcquireSubagentSlot(): boolean` and `releaseSubagentSlot(): void`, using the single-threaded check-then-increment pattern (`activeSubagentCount >= SUBAGENT_MAX_PER_TURN` -> false, else increment). Release in `finally` on every path, including timeout, abort, empty report, and unexpected error. Clamp at zero defensively.
   - Return `{ error: "All 5 subagent slots are busy. Wait for a running subagent to finish and try again." }` when acquisition fails.
2. `src/lib/tools/registry.ts`: pass `depth` from options (default `0`) into `createSubagentTool` and only register the tool when `depth < SUBAGENT_DEPTH`, so a future nested toolset cannot expose it even if `buildResearchTools` changes.
3. `src/lib/subagent.ts`: confirm the nested `generateText` never sets `tools.spawnSubagent` (it uses `buildResearchTools()`), so depth is enforced twice: absent tool plus explicit guard.
4. No store changes. The counters live in module scope in one tool file and reset on app reload, matching the transient nature of the feature.
5. `src/lib/subagent-approval.ts`: confirm the FIFO queue is the only path that promotes a request to active, that a denied or cancelled request never acquires a slot, and that resolving a stale id is a no-op. If two parallel calls arrive before the first decision, the dialog shows the first task, then the second after the first resolves.
6. `src/lib/tools/subagent.ts`: acquisition order is depth guard -> per-turn counter -> approval -> in-flight slot -> `runSubagent`. A denied or cancelled approval must return before `tryAcquireSubagentSlot`, so a user who leaves a dialog open does not hold one of the five slots.

## Completion criteria

- `spawnSubagent` exists as an AI SDK tool with a focused description and a `{ task: string }` schema, runs on the parent's current provider and model read at execution time, and returns a concise report via the parent turn.

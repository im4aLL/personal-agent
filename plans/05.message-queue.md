# 05 - Message queue while the assistant is generating

## Goal

While a conversation's turn is running, the composer stays usable: the user types the next message, presses Enter, and it is queued instead of being blocked by a disabled textarea. When the turn ends successfully the head of that conversation's queue is sent automatically, then the next one, until the queue is empty. Stop and error end the automatic chain and leave the remaining items visible and removable, with an explicit Resume action.

Queued items are per conversation and survive switching conversations, including the case where the queue belongs to a conversation that is no longer selected. The queue is transient in the strictest sense: it lives only in the in-memory Zustand transient slice created by plan 01, is never written to Turso, never written to `localStorage`, and disappears on reload. A queued item only reaches persistence when it becomes a real message through the existing `addMessage` path, exactly like a normal send.

## Assumptions and decisions

- **Dependency on plan 01.** This plan assumes `plans/01.conversation-activity-indicator.md` has landed: `src/store/chat-transient.ts` and `chat-transient.types.ts` exist, `conversationActivity` is the single source of `isGenerating`, and `src/hooks/chat-stream-lifecycle.ts` owns the per-conversation `AbortController` registry. If plan 05 were built first, it would have to create the same files and plan 01 would then extend them; the milestone order in this plan requires plan 01 first because both plans edit `streamAssistantResponse` and the transient slice.
- **One transient store, extended, not duplicated.** The queue is added to plan 01's `ChatTransientSlice` as `conversationQueues`. No new store, no separate module-level Map of pending messages. The module-level piece this plan adds is a drain guard and drain loop, not state.
- **Explicit conversation send path.** `src/hooks/use-chat.ts` `sendMessage` currently resolves its target with `selectSelectedConversation(useChatStore.getState())`. That is the blocker named in the requirements. This plan introduces `sendMessageToConversation(conversationId, content, attachments)` which never reads the selection, and `sendMessage` becomes a thin wrapper that reads the selected id once, at call time, and delegates. Every other turn starter (`regenerate`, `editMessage`, `retry`) already uses `conversation.id` or a concrete id, so no second streaming implementation is created anywhere.
- **Turn outcome is reported, not inferred.** `streamAssistantResponse` becomes the single place that decides how a turn ended, returning `TurnOutcome = "success" | "stopped" | "error" | "blocked"`. The queue flush is driven by that return value, never by watching `conversationActivity`.
- **Where the flush runs.** The drain runs inside the async body that already started the turn: `sendMessage` awaits `sendMessageToConversation` and, on `"success"`, awaits `drainConversationQueue(conversationId, sendMessageToConversation)`. That async body is alive after `MessageInput` unmounts (it is keyed by conversation id in `chat-area.tsx`), so a switch to conversation B does not stop A's flush, and nothing depends on the hook instance that the user happens to be looking at. The closure that keeps running is the one that started A's turn; every value it needs beyond the conversation id is resolved from `useChatStore.getState()` at flush time.
- **Resolve provider, model, thinking level, and system prompt at flush time.** This is a real behavior change, needed by the queue and correct on its own: the model selector is not disabled during generation, so a turn must use the model that is selected when it starts, not the one selected when some earlier render happened. `resolveTurnContext()` reads `providers`, `selectedModel`, and `thinkingLevel` from the store at call time; `buildCurrentSystemPrompt()` is already called at send time. `streamAssistantResponse` and `runCompaction` stop reading those values from the render closure, and their dependency arrays shrink accordingly.
- **Slash commands are parsed exactly once, when the message is actually sent.** The queue stores the raw composer text, slash prefix included. Parsing and `activateSkill` / `activateAgent` still happen only in `sendMessageToConversation`, so a queued `/skill hello` activates once at its own turn start and deactivates once at its turn end. Parsing at enqueue time would run activation twice; storing the parsed result would freeze the skill content the user might have edited in between.
- **Attachments are in-memory objects, already base64.** A `QueuedMessage` holds the same `Attachment[]` that a normal send would pass, by reference (no copy of `data`). Existing limits still apply: 10 MB per file, and the file-type allow-list in `message-input.tsx`.
- **The subagent opt-in travels with the queued item.** If plan 04 has landed, the composer's one-shot `Allow subagents` flag is captured into `QueuedMessage.allowSubagents` when the item is enqueued, not read from the composer when it flushes. A queued message therefore keeps the consent the user gave when writing it, and a later toggle change cannot retroactively approve an earlier queued item.
- **Cap: 20 items per conversation.** `MAX_QUEUED_MESSAGES = 20`, enforced in the store action which returns `false` when full so the caller can toast. Items are counted, not bytes; worst case memory is 20 items with the existing 10 MB per-attachment limit, which is the same order as 20 real messages in the store. A byte-based cap is deliberately not added.
- **Exact semantics.** `paused` is derived (`queue.length > 0 && !isGenerating` from plan 01's activity), so it needs no new state and cannot disagree with the spinner in the sidebar.

| Event | What happens to the queue |
| --- | --- |
| Turn ends `success` | Dequeue head, send it, repeat until empty. One turn at a time, strictly in order. |
| User stop (Stop button, Escape, abort signal) | No further sends. Remaining items stay in place, queue reads as paused, Resume available. Nothing is dropped. |
| Provider error after retries exhausted | Same as stop: no further sends, items stay, paused. The failing item is not re-queued because it already exists as a user message with an error reply. |
| Blocked before anything is sent (no active provider, conversation messages not loaded, or conversation deleted) | Nothing is sent. The item is put back at the head of the queue and the drain stops. |
| Auto-compaction failure that ends as "Conversation too long to send" | The user message was already added, so this is an `error` outcome: no flush, items stay. |
| User deletes the conversation | `clearConversationQueue` drops the queue with the conversation. A late drain cannot recreate it. |
| Reload / app restart | Queue is gone. Nothing was persisted. |
| Enqueue while a drained turn is running | Appended at the tail; the running drain loop re-reads the head each iteration, so it is picked up in order. |

- **Keyboard, decided.** Enter while a turn is running enqueues (Shift+Enter still inserts a newline). Enter with the slash autocomplete open still selects the highlighted skill/agent, unchanged. Escape keeps its current meaning, stop the running turn if one exists, otherwise close the slash popover, otherwise clear the textarea. Escape never clears the queue: stopping a turn is not a request to discard the queued messages. Manual sends always jump the queue (Enter when idle sends immediately and then drains the queue on success); a queued item is never silently reordered.
- **Queue visibility is limited to the selected conversation.** A queue that pauses in a conversation the user has switched away from stays paused silently until they return (plan 01's sidebar spinner already tells them a turn ran there). A sidebar badge for paused queues is deferred.
- **Known side effect, accepted.** Slash activation is global agents state. If a queued `/skillname` message flushes while the user is in another conversation, that skill is activated and deactivated globally for the duration of that turn, so the composer chips in the visible conversation may flicker. Documented, not worked around.
- **No automated tests, per project instructions.** Verification is manual plus `npm run lint` (`biome check`) and `npm run build` (`tsc && vite build`) as correctness gates.

## Proposed structure

```text
src/store/
  chat-transient.types.ts        (extend: QueuedMessage, queue fields + actions on ChatTransientSlice)
  chat-transient.ts              (extend: conversationQueues slice, MAX_QUEUED_MESSAGES, id + selector helpers)
  chat.ts                        (existing: deleteConversation also clears the queue)
src/hooks/
  chat-stream-lifecycle.ts       (plan 01, extend: hasActiveConversationTurn)
  chat-turn-runner.ts            (new: drainConversationQueue, module-level drain guard)
  chat-turn-runner.types.ts      (new: TurnOutcome, SendTurnFn)
  use-chat.ts                    (existing: resolveTurnContext, sendMessageToConversation, outcomes, queue actions)
src/components/chat/
  queued-messages.tsx            (new: compact chip rows above the composer)
  message-input.tsx              (existing: editable while generating, Enter queues, Queue button)
ARCHITECTURE.md                  (sections 3, 4, 7)
```

Responsibilities:

- `chat-transient.types.ts` holds the queue data contract only (`QueuedMessage`) and the extended slice contract. No runtime values.
- `chat-transient.ts` owns the queue slice plus the two small runtime helpers that belong with it (`createQueuedMessageId`, `selectConversationQueue`) and the cap constant. It writes nothing outside state.
- `chat-turn-runner.ts` owns exactly one responsibility: "given a conversation and a way to send one message, run turns back to back until the queue empties or a turn does not succeed". It holds no queue data, only the `Set` that prevents two concurrent drains of the same conversation. It is plain TypeScript with no React imports.
- `use-chat.ts` keeps ownership of the turn itself and gains one explicit-send entry point plus four thin queue actions. Its orchestration stays in one place; the drain loop is not inlined into it.
- `queued-messages.tsx` is purely presentational: text, attachment count, remove, resume, clear, paused label.

## Milestone 1: Queue during a running turn, flush on success

### Outcome

While conversation A is generating, the textarea is editable. Typing `second message` and pressing Enter clears the composer and adds a small row above it reading `second message` with a remove button; a second submit adds a second row. When A's turn completes successfully, the first row turns into a real user message and A starts generating again; the second row follows when that turn completes. Pressing Stop leaves the remaining rows in place with a Resume button. Switching to B mid-turn does not prevent A's queue from flushing.

### Implementation

1. `src/store/chat-transient.types.ts` (extend plan 01's file, importing `Attachment` with `import type`):
   - `QueuedMessage` with TSDoc: `{ id: string; content: string; attachments?: Attachment[]; allowSubagents?: boolean }`. `content` is the raw composer text, slash prefix intact; order is array order, no timestamp. `allowSubagents` is the one-shot subagent consent captured at enqueue time from plan 04; it is optional so this plan still works if plan 04 has not landed.
   - Extend `ChatTransientSlice` with `conversationQueues: Record<string, QueuedMessage[]>` and four documented actions: `enqueueMessage(conversationId, message): boolean`, `removeQueuedMessage(conversationId, messageId): void`, `requeueQueuedMessage(conversationId, message): void`, `clearConversationQueue(conversationId): void`.
2. `src/store/chat-transient.ts` (extend `createChatTransientSlice`, keeping plan 01's setter-only signature and its structural `set` typing; no `get`):
   - `export const MAX_QUEUED_MESSAGES = 20;` with TSDoc explaining it bounds one conversation's queue, not the session.
   - `export function createQueuedMessageId(): string` returning `queued-${Date.now()}-${Math.random().toString(36).slice(2)}`.
   - `export function selectConversationQueue(state: Pick<ChatTransientSlice, "conversationQueues">, conversationId: string | null | undefined): QueuedMessage[]` returning a module-level `EMPTY_QUEUE` constant when the id is null, missing, or the queue is absent. The constant matters: a fresh `[]` per call would make the Zustand v5 selector snapshot unstable and loop.
   - `enqueueMessage`: append immutably, return `false` without changing state when the current length is already `MAX_QUEUED_MESSAGES`. Replace only the touched conversation key.
   - `removeQueuedMessage`: filter by id; delete the conversation key when the result is empty; no-op when nothing matched (return no partial state).
   - `requeueQueuedMessage`: prepend, skipping if the id is already present (idempotent).
   - `clearConversationQueue`: delete the key; no-op when absent.
   - TSDoc on every exported declaration, each stating that the state is memory-only and never persisted.
3. `src/store/chat.ts`: in `deleteConversation`, next to plan 01's `get().setConversationActivity(id, null)` after the main `set`, call `get().clearConversationQueue(id)`.
4. `src/hooks/chat-turn-runner.types.ts` (new):
   - `export type TurnOutcome = "success" | "stopped" | "error" | "blocked";` documented per value, including that `"blocked"` means nothing was added to the conversation.
   - `export type SendTurnFn = (conversationId: string, content: string, attachments?: Attachment[], options?: { allowSubagents?: boolean }) => Promise<TurnOutcome>;`
5. `src/hooks/chat-turn-runner.ts` (new):
   - module-level `const drainingConversations = new Set<string>();` documented as the double-drain guard.
   - `export async function drainConversationQueue(conversationId: string, send: SendTurnFn): Promise<void>`: return immediately if the id is already draining or `hasActiveConversationTurn(conversationId)`; add to the set; loop: read `useChatStore.getState().conversationQueues[conversationId]?.[0]`; stop when there is no head; call `removeQueuedMessage(conversationId, head.id)`; `await send(conversationId, head.content, head.attachments, { allowSubagents: head.allowSubagents })`; on `"blocked"` requeue the head, log in DEV, and stop; on anything other than `"success"` stop; finally remove the id from the set. Wrap the loop in `try/catch` so an unexpected rejection stops the drain instead of escaping as an unhandled rejection from a `void` call.
   - The loop re-reads the head every iteration, so items enqueued while the drain is running are picked up in order.
6. `src/hooks/use-chat.ts`:
   - Add a module-level `resolveTurnContext()` returning `{ provider, selectedModel, thinkingLevel }` from `useChatStore.getState()`, or `null` when the selected provider is missing. TSDoc: resolves the values a turn must use right now, at call time, so a queue flush or a model change mid-turn is honored.
   - `runCompaction`: resolve provider and model through `resolveTurnContext()` instead of reading `activeProvider` / `selectedModel` from the closure; drop them from the dependency array. Behavior for the manual button is unchanged apart from using live values.
   - `streamAssistantResponse`: return `Promise<TurnOutcome>`; resolve `providers`, `selectedModel`, `thinkingLevel`, and the provider through `resolveTurnContext()` at the top; `!provider` returns `"blocked"` before plan 01's `startConversationTurn`. Track a local `outcome` and set it at each exit: compaction abort (`AbortError` during auto-compaction) `"stopped"`; "Conversation too long to send" `"error"`; user abort (`receivedAbort || signal.aborted`) `"stopped"`; clean finish `"success"`; `AbortError` in the catch `"stopped"`; retries exhausted or non-retryable `"error"`. Keep plan 01's single `try/finally` and return the outcome after it. Keep every existing retry, partial-output, title-generation, toast, and DEV logging behavior untouched; use `turnController.signal` from plan 01 for both `streamText` and compaction.
   - New `sendMessageToConversation(conversationId, content, attachments?, options?: { allowSubagents?: boolean })` (extracted from today's `sendMessage`):
     - guard `resolveTurnContext()` and `isCompacting` -> `"blocked"`; trim and reject empty content without attachments -> `"blocked"`;
     - keep the slash parsing block exactly as is (activation happens here, once);
     - resolve the conversation by id from the store (`conversations.find`) plus a `loadedConversationIds.has(conversationId)` guard -> `"blocked"` when missing or not loaded, so a flush can never send an empty history;
     - `addMessage(conversationId, userMessage)`, `await streamAssistantResponse(conversationId, [...conversation.messages, userMessage], buildCurrentSystemPrompt(), { allowSubagents: options?.allowSubagents === true })` inside `try/catch` that maps a throw to `"error"` with a DEV log;
     - move the one-shot `deactivateSkill` / `deactivateAgent` block so it runs after the call regardless of outcome (it is the closest existing behavior and also fixes a latent leak when a turn throws);
     - return the outcome.
   - `sendMessage(content, attachments, options?)`: read `selectedConversationId` and return early when null; `const outcome = await sendMessageToConversation(conversationId, content, attachments, options)`; when `outcome === "success"`, `await drainConversationQueue(conversationId, sendMessageToConversation)`; keep the public `Promise<void>` shape so `retry` is unchanged.
   - New `resumeQueue()`: read the selected id, `void drainConversationQueue(id, sendMessageToConversation)`.
   - New queue actions for the UI: `enqueueMessage(content, attachments, options?: { allowSubagents?: boolean })` (build the item with `createQueuedMessageId` and the flag, call the store action, toast `"Queue is full"` with `"Up to 20 messages can wait. Remove one or wait for the current reply."` when it returns `false`), `removeQueuedMessage` is not needed in the hook since the component has the id, `clearQueue()` for later milestones.
   - Return `resumeQueue` and `enqueueMessage` from `useChat`. Do not return the queue data from the hook, so `MessageList`'s `useChat()` call does not subscribe to queue changes.
7. `src/components/chat/queued-messages.tsx` (new): `interface QueuedMessagesProps { messages: QueuedMessage[]; isPaused: boolean; onRemove: (messageId: string) => void; onResume: () => void; }` (local interface, matching `MessageBubble` / `ThinkingBlock` style). Returns `null` when empty. Renders `role="list"` with one `role="listitem"` row per item: truncated text (`truncate`, `max-w-48`), a `PaperclipIcon` plus `2 attachments` when present, and a remove button with `aria-label={`Remove queued message ${preview}`}`. 8. `src/components/chat/message-input.tsx`:
   - Subscribe: `const conversationId = conversation?.id ?? null;` and `const queuedMessages = useChatStore((state) => selectConversationQueue(state, conversationId));` (the shared empty constant keeps the snapshot stable).
   - Destructure `enqueueMessage` and `resumeQueue` from `useChat()`.
   - Extract a `submitComposer()` helper from `handleSend`: validation and toasts stay in one place, then `isGenerating ? enqueue : send`. `handleSend` becomes the non-generating path; the generating path calls `enqueueMessage(trimmed || "Hello", attachments, { allowSubagents })` only when the same `canSend` / length / content checks pass, then clears value and attachments. ## Milestone 2: One turn at a time, every turn starter drains, deletion cannot resurrect

### Outcome

No queued message can ever be sent twice, and no second turn can start in a conversation that is already streaming. A queue that is waiting when the user regenerates an answer or edits a message also flushes on success. Deleting a conversation cannot bring its queue back through a late drain.

### Implementation

1. `src/hooks/chat-stream-lifecycle.ts` (plan 01's module): add `hasActiveConversationTurn(conversationId): boolean` reading the module-level controller registry, with TSDoc noting that it answers "is a turn registered" without aborting or writing activity.
2. `src/hooks/chat-turn-runner.ts`:
   - Re-check `hasActiveConversationTurn(conversationId)` immediately before each `send`, not only on entry, and stop if a turn is somehow live (defensive against a Resume click racing the tail of a turn).
   - On `"blocked"`, requeue the head only when the conversation still exists: read `useChatStore.getState().conversations.some((item) => item.id === conversationId)`; skip the requeue when it is gone so a delete-then-block cannot recreate `conversationQueues[deletedId]`. DEV log both branches.
3. `src/hooks/use-chat.ts`:
   - `regenerate`: capture the outcome of `await streamAssistantResponse(...)`; on `"success"` call `void drainConversationQueue(conversation.id, sendMessageToConversation)`.
   - `editMessage`: same.
   - `retry`: unchanged, because it delegates to `sendMessage`, which already drains.
   - Add the new callbacks to the existing dependency arrays.
4. Re-read `sendMessageToConversation` for duplicate-send hazards: the drain removes the item before sending, and the only path that can send twice is two concurrent drains, which the `drainingConversations` set and the active-turn guard both prevent. Confirm no drain is started from a `useEffect`, so React double-render and StrictMode double-mount cannot duplicate a flush.

3. Queue two items in A, switch to B, and while A's first queued turn is running, press Resume in A's row (via a temporary DEV button or by switching back at the right moment): no second turn starts, and the sidebar shows one turn.
4. Queue an item in A, then delete A from the sidebar while A is generating: the conversation disappears, no queued work runs, no console error, and the queue map has no entry for that id (temporary DEV log of `Object.keys(useChatStore.getState().conversationQueues).length`, removed afterwards).

### Deliberately deferred

- Parallel drains across conversations (they are independent by key and already work; no scheduling is added).
- Queue-aware cancellation policy on conversation delete beyond dropping the queue and plan 01's stream abort.

## Completion criteria

- While a turn is generating, the composer accepts text and submits it into a per-conversation queue; queued items are shown as compact rows with text, attachment count, and a remove control.
- On a successful turn the queue flushes automatically, in order, one turn at a time, reusing the existing streaming path with no second implementation.
- A queue that belongs to a conversation the user has switched away from still flushes when that conversation's turn ends; nothing is sent to the visible conversation.
- Stop, Escape, and provider errors never discard queued items and never continue the flush; remaining items stay visible with an explicit Resume.
- The queue is capped at 20 per conversation with a friendly error, is cleared when the conversation is deleted, and never survives a reload.
- Every queued send resolves the provider, model, thinking level, and system prompt at flush time, parses slash commands exactly once, and cannot be sent twice or start a second concurrent turn.
- Nothing in this feature writes to Turso or `localStorage`; no migration, schema, `Message`, or `saveMessage` change is made.
- `ARCHITECTURE.md` reflects the transient queue and the explicit send path; every new declaration carries TSDoc; `npm run lint` and `npm run build` pass; the manual checklist above is completed by the user.

## Quality check

- Observable result early: Milestone 1 ends with visible queued rows and messages that actually send in order.
- Milestone 1 runs independently: slice, drain runner, explicit send path, and one presentational component are enough to see the whole flow.
- Each milestone builds on a working flow: Milestone 2 hardens correctness on a queue that already works; Milestone 3 only clarifies the proven state.
- Runnable after every milestone: no milestone leaves a half-wired store, an unrendered slice, or a dead-end queue.
- Architecture sufficient but not speculative: one transient slice extension, one small runner, one component, no interfaces for hypothetical transports or persistence.
- Cohesion and size: the drain lives outside the already oversized `use-chat.ts`; the queue stays out of `chat.ts`; `QueuedMessage` and the slice contract live in `chat-transient.types.ts`; the send path is one explicit function instead of a second streaming path.
- Required declaration docs ship with the implementation; TypeScript named contracts stay in sibling `.types.ts` files.
- UI appears before infrastructure: no settings, no persistence, no schema work, no new store.
- Safeguards and edge cases come after the working flow: pause/resume, cap, one-turn guard, requeue-on-blocked, and lifecycle cleanup follow the proven queue.
- Testing: no automated tests by project instruction; verification is manual, concrete, and numbered, with lint and build as correctness gates.
- Deferred work is explicit per milestone, including the known limitation that a paused queue in a background conversation is only visible on return.

# 02 - Tool-call count per assistant turn

## Goal

While an assistant turn runs, and afterwards for the rest of the session, the user can see how many tools the model called for that specific assistant message (for example `3 tool calls`) rendered as a compact row inside the assistant bubble, expandable to show each tool name and its status.

The number is session-only: it lives in memory, survives switching between conversations, and disappears on app reload. Nothing is written to Turso and nothing is written to `localStorage`.

## Assumptions and decisions

- **Unit of counting (assumption, reversible):** one count per assistant message, aggregating every AI SDK step of that `streamText` run. `streamText` is called with `stopWhen: stepCountIs(8)`, so one assistant message can contain several sequential tool calls; the count sums all of them.
  **Open decision for the user:** the alternative is a per-conversation running total. That changes the unit, the keying (`conversationId` instead of `messageId`), and the placement (chat header, not the bubble). This plan does not build it. The slice is keyed per message, so a later conversation total is a derived sum, not a redesign.
- **Storage:** a transient Zustand slice field `messageToolActivity: Record<string, MessageToolActivity>` composed into `useChatStore`, not a `Message` field. `saveMessage` in `src/lib/turso-repository.ts` uses an explicit column list (`reasoning` is already excluded on purpose), and adding persistence-adjacent fields to `Message` invites accidental persistence later. Keying by assistant `messageId` matches the unit above and guarantees isolation when two conversations stream at once (ids are globally unique via `createMessageId`).
- **Where the slice is written:** `useChatStore` stays the single transient-state owner, matching plan 01 (`plans/01.conversation-activity-indicator.md`). Plan 01 creates `src/store/chat-transient.ts` plus `src/store/chat-transient.types.ts` with `conversationActivity`. This plan extends those same files with the message tool slice; it does not create a second transient store or a competing module. If plan 02 lands first, create the module with only the tool slice and let plan 01 extend it the same way.
- **No competing store:** do not create `useChatTransientStore`. One store, one slice module.
- **Read path:** `MessageBubble` selects only its own entry (`useChatStore((state) => state.messageToolActivity[message.id])`). `MessageList` must not subscribe to the map, otherwise every tool event re-renders every message.
- **Write path:** `useChat`'s stream loop calls the slice actions through `useChatStore.getState()`, matching the existing one-off `getState()` reads in that callback and avoiding three more entries in its large dependency array.
- **Statuses:** `running | succeeded | failed`. Tool `execute` functions in `src/lib/tools/*` mostly return `{ error }` objects rather than throwing, so an HTTP failure typically settles as `succeeded` with an error-shaped output. Only thrown/validation failures produce `tool-error` -> `failed`. The UI must therefore stay honest and say what the SDK reported, not what the tool "meant".
- **Dev logging is preserved:** the `import.meta.env.DEV` console block in the stream loop, including the `recall` -> `lastRecallTokens` accounting and the phase updates from plan 01, must keep behaving exactly as today. Only new non-DEV calls are added around it.
- **Component props stay local:** this repo declares local `interface XProps` inside component files (`MessageBubbleProps`, `ThinkingBlockProps`). Follow that for the new component; keep feature state contracts in `chat-transient.types.ts`.
- **Styling:** Tailwind utility classes and existing tokens (`text-muted-foreground`, `text-destructive`, `bg-muted/30`). No new CSS files, no BEM blocks here because the repo's chat components are utility-class based.
- **No automated tests:** per project instructions the user tests manually. This plan ends with a manual checklist instead of a testing milestone.

## Proposed structure

Existing files that matter:

- `src/hooks/use-chat.ts` - owns the stream loop (`streamAssistantResponse`), retry attempts, abort handling; currently only DEV-logs `tool-call` / `tool-result` / `tool-error` in the `for await` loop.
- `src/store/chat.ts` - `useChatStore`, `ChatState`, and the message lifecycle actions `addMessage`, `deleteMessage`, `regenerate`, `editMessage`, `deleteConversation`, plus the module-level `selectSelectedConversation`. About 1370 lines, so new transient state stays out of it.
- `src/store/chat-transient.ts` and `src/store/chat-transient.types.ts` - created by plan 01 for conversation turn activity. Extended here.
- `src/components/chat/message-bubble.tsx` - renders `ThinkingBlock`, then attachments, then `Markdown`, then the streaming spinner, then the model metadata line and the hover action row.
- `src/components/chat/thinking-block.tsx` - the existing compact collapsible pattern to mirror for details.
- `src/components/ui/collapsible.tsx` - Radix `Collapsible`, already used by `ThinkingBlock`.
- `src/lib/types/chat.ts` - `Message`, `ThinkingBlock`; unchanged by this feature.
- `src/lib/turso-repository.ts` - `saveMessage` explicit column list; unchanged, and must stay unchanged.

New files:

- `src/components/chat/tool-activity.tsx` - `ToolActivity` presentational component (count row in Milestone 1, collapsible details in Milestone 2), plus a `TOOL_LABELS` map.

Added to the existing transient module from plan 01:

- `src/store/chat-transient.types.ts` - `ToolCallStatus`, `ToolCallActivity`, `MessageToolActivity`; extend `ChatTransientSlice` with the `messageToolActivity` map and its actions.
- `src/store/chat-transient.ts` - `startToolCall`, `settleToolCall`, `resetMessageToolActivity`, `clearMessageToolActivity`, `clearConversationToolActivity` inside the existing `createChatTransientSlice`.

Data flow:

```text
streamText fullStream part
  -> use-chat.ts stream loop
     -> useChatStore.getState().startToolCall / settleToolCall
        -> chat-transient.ts slice: messageToolActivity[messageId].calls
           -> MessageBubble selector (its own entry only)
              -> ToolActivity (count, optionally details)
```

## Milestone 1: Live count row per assistant turn

### Outcome

A real tool-using turn shows a compact row inside the assistant bubble reading `1 tool call` (or `3 tool calls`) with a wrench icon, updating live as the model calls tools. Turns without tools show nothing. The count survives switching conversations, and is gone after reload.

### Implementation

1. `src/store/chat-transient.types.ts` (extend the file created by plan 01):

```ts
/** Settlement state of one tool call as reported by the AI SDK stream. */
export type ToolCallStatus = "running" | "succeeded" | "failed";

/** One model-requested tool call inside a single assistant turn. */
export type ToolCallActivity = {
  toolCallId: string;
  toolName: string;
  status: ToolCallStatus;
};

/** Transient tool activity for one assistant message. Never persisted. */
export type MessageToolActivity = {
  conversationId: string;
  calls: ToolCallActivity[];
};
```

   Extend `ChatTransientSlice` with:

```ts
messageToolActivity: Record<string, MessageToolActivity>;
startToolCall: (messageId: string, conversationId: string, toolCallId: string, toolName: string) => void;
settleToolCall: (messageId: string, toolCallId: string, status: ToolCallStatus) => void;
resetMessageToolActivity: (messageId: string) => void;
clearMessageToolActivity: (messageId: string) => void;
clearConversationToolActivity: (conversationId: string) => void;
```

   Document each type with a TSDoc summary. `conversationId` is stored on the entry so `clearConversationToolActivity` does not need conversation messages to be loaded.

2. `src/store/chat-transient.ts` (extend the existing `createChatTransientSlice`): initial `messageToolActivity: {}`. Behaviour:
   - `startToolCall`: append `{ toolCallId, toolName, status: "running" }` to the entry's `calls`, creating the entry if absent. Replace only that entry: `{ ...state.messageToolActivity, [messageId]: { ...entry, calls } }` so untouched entries keep their reference.
   - `settleToolCall`: map `calls`, set `status` where `toolCallId` matches. No match -> return `{}` (no state change).
   - `resetMessageToolActivity` / `clearMessageToolActivity`: delete the key. `clearConversationToolActivity`: drop every entry whose `conversationId` matches.
   - Use the same structural setter type introduced by plan 01, widened if needed to accept a `Partial<ChatTransientSlice>`. All updater-based actions return partial state so the setter stays simple.
   - Every exported function gets a TSDoc block describing effect and that it is memory-only.

3. `src/store/chat.ts` - no structural change if plan 01 already composed the slice; only verify `ChatState` includes the extended slice. If plan 02 lands first, compose `createChatTransientSlice(set)` as described in plan 01.

4. `src/hooks/use-chat.ts` - wire the stream loop, inside the existing `else` branch of the `for await (const part of stream)` loop, before the `import.meta.env.DEV` block. Combine with plan 01's phase updates:

```ts
if (part.type === "tool-call") {
  store.startToolCall(assistantMessage.id, conversationId, part.toolCallId, part.toolName);
  updateConversationTurnPhase(conversationId, "tool", part.toolName);
} else if (part.type === "tool-result") {
  store.settleToolCall(assistantMessage.id, part.toolCallId, "succeeded");
  updateConversationTurnPhase(conversationId, "streaming");
} else if (part.type === "tool-error") {
  store.settleToolCall(assistantMessage.id, part.toolCallId, "failed");
  updateConversationTurnPhase(conversationId, "streaming");
}
```

   where `const store = useChatStore.getState();` is read once per part (or once per attempt) with `startToolCall` / `settleToolCall` destructured. Keep the `abort` / `finish` capture above it and the whole DEV block below it untouched, including the `recall` branch that calls `setLastRecallTokens`.
   Add the retry reset in the existing `if (attempt > 0)` block, right next to `setMessageOutput(...)`: `resetMessageToolActivity(assistantMessage.id)`, with a short comment that a retry restarts the count instead of duplicating it.

5. `src/components/chat/tool-activity.tsx` (new) - Milestone 1 version:

```tsx
interface ToolActivityProps {
  calls: ToolCallActivity[];
}

export function ToolActivity({ calls }: ToolActivityProps) { ... }
```

   Renders nothing when `calls.length === 0`. Otherwise a single row: `WrenchIcon` (`aria-hidden`, `size-3.5`) + `{calls.length} tool call` / `{calls.length} tool calls`, `text-xs text-muted-foreground`, plus a `Loader2Icon size-3 animate-spin` while `calls.some((call) => call.status === "running")`. TSDoc the component.

6. `src/components/chat/message-bubble.tsx` - subscribe and place:
   - `const toolActivity = useChatStore((state) => state.messageToolActivity[message.id]);`
   - render `{!isUser && toolActivity && <ToolActivity calls={toolActivity.calls} />}` between the `ThinkingBlock` block and the attachments/`Markdown` block. Order becomes: error banner -> thinking -> tool activity -> attachments -> answer text -> streaming spinner -> error text.
   - the model metadata line and hover actions stay where they are, below the bubble; do not merge the tool row into that line (metadata is about the model, the row is about the turn).
   - import `ToolActivity` and `useChatStore`; no prop changes, so `MessageList` is untouched.

### Verification

1. `npm run lint` and `npm run build` pass.
2. `npm run tauri dev`, open Settings > Tool, enable "URL fetching".
3. Pick a non-Gemini model (tools are disabled for Gemini via `isGeminiProvider`). Send: `Fetch https://example.com and tell me the page title.`
4. Observe inside the assistant bubble: the row appears with a spinner and `1 tool call` while the fetch runs, then the spinner disappears and the answer streams below it.
5. Send `Fetch https://example.com and https://www.iana.org/help/example-domains and compare them.` and confirm the count reaches `2 tool calls` within the same bubble.
6. Send `Say hello.` and confirm no tool row appears.
7. Switch to another conversation and back: the count is still shown. Reload the app (or close and reopen the Tauri window): the assistant text is still there and the tool row is gone.
8. With Turso configured, confirm after reload that the assistant message text loads normally (proves `messages` persistence is untouched), and that `src/lib/turso-repository.ts` and `src/lib/config.ts` were not modified in this change.

## Milestone 2: Expandable per-call details

### Outcome

Clicking (or keyboard-activating) the row expands a short list of the tools used in that turn, for example `Fetch URL - done`, `Web search - failed`, `Recall - running`. Collapsed by default so the chat stays clean.

### Implementation

1. `src/components/chat/tool-activity.tsx` - extend the component, still one file, still one responsibility (presenting tool activity):
   - add `const TOOL_LABELS: Record<string, string> = { fetchUrl: "Fetch URL", webSearch: "Web search", googleSearch: "Google search", duckduckgoSearch: "DuckDuckGo search", createPdf: "Create PDF", remember: "Remember", recall: "Recall" };` with a `toolLabel(toolName)` helper that falls back to the raw tool name so new tools never render blanks.
   - replace the static row with `Collapsible` / `CollapsibleTrigger` / `CollapsibleContent` mirroring `ThinkingBlock`: a `<button type="button">` trigger with `aria-expanded`, `ChevronRightIcon` / `ChevronDownIcon`, the existing wrench + count + running spinner, and the same focus ring classes (`focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-ring rounded-sm`).
   - details body: `<ul>` of `<li>` rows, each `flex items-center justify-between gap-2 text-xs`. Left: `toolLabel(call.toolName)` truncated with `max-w-48 truncate`, `title={call.toolName}`. Right: status text `Running` / `Done` / `Failed` with `text-muted-foreground` for running/done and `text-destructive` for failed. Container styling: `mt-1.5 rounded-md border-l-2 border-muted-foreground/30 bg-muted/30 p-2` to match the thinking block.
   - keep local open state (`useState(false)`) - collapse state is per bubble and must not be stored anywhere.
   - TSDoc any new named helper.

### Verification

1. `npm run lint`, `npm run build`, `npm run tauri dev`.
2. Re-run the two fetch turns: the row stays collapsed by default and shows only the count.
3. Click the row: the list shows `Fetch URL - Done` per call; clicking again collapses it.
4. Keyboard: `Tab` reaches the row, focus ring is visible, `Enter` and `Space` toggle it, screen reader announces expanded/collapsed via `aria-expanded`.
5. Switch to light theme and dark theme: text, spinner, and failed color remain readable in both.
6. While a call is in flight the list shows `Running`; when it settles it flips to `Done` without the row jumping between collapsed and expanded.

### Deliberately deferred

- Call arguments and outputs, durations, tokens, per-call timestamps, grouping by step.
- Reordering by step index, per-call retry attempts.
- Persistent or cross-session history of tool activity.

## Milestone 3: Session lifecycle cleanup and multi-conversation isolation

### Outcome

Tool activity is removed when its message or conversation disappears, so the map stays bounded in long sessions, and two conversations streaming at the same time never affect each other's counts.

### Implementation

1. `src/store/chat.ts` - call the slice actions where messages are removed (one-line additions, no behaviour change elsewhere):
   - `deleteMessage`: `get().clearMessageToolActivity(messageId)` inside the `set` callback (use the already-available `state`/`get()` form used by the surrounding code).
   - `regenerate`: before/while slicing the last assistant message off, capture it and call `clearMessageToolActivity` for its id. `regenerateMessages` returns `messages.slice(0, -1)`, so the dropped id is `conversation.messages[conversation.messages.length - 1]?.id` when that message is the assistant one.
   - `editMessage`: `applyMessageEdit` returns `[...messages.slice(0, index), editedTarget]`, so everything after `editedMessages.length` is dropped. Clear those ids: `for (const message of conversation.messages.slice(editedMessages.length)) { clearMessageToolActivity(message.id); }`.
   - `deleteConversation`: `clearConversationToolActivity(id)` before returning the new state, so it does not depend on messages being loaded. Combine with plan 01's `setConversationActivity(id, null)`.
2. `src/store/chat-transient.ts` - only if needed, small corrections so the actions above are safe to call more than once (deleting a missing key must return `{}` and keep state identity).

### Verification

1. `npm run lint`, `npm run build`.
2. Temporary dev-only check (add, verify, then remove before finishing): a `useEffect` in `MessageList` or the stream loop logging `Object.keys(useChatStore.getState().messageToolActivity).length` in DEV.
   - After a tool turn: length is 1.
   - Regenerate the answer: length returns to 1 with the new message id (old id gone).
   - Edit the user message: length drops to 0 for the dropped assistant messages.
   - Delete the message or the conversation: length drops accordingly.
   - Remove the temporary log.
3. Isolation: in conversation A send a tool turn, immediately switch to conversation B and send a plain turn. B shows no count; switching back to A shows A's own count and it kept incrementing only from A's stream.
4. Reload the app: all counts are gone while both conversations still load their messages from Turso.

### Deliberately deferred

- Cancelling an in-flight stream when its conversation is deleted (plan 01 Milestone 2 covers this).
- Any garbage collection timer or size cap (bounded in practice by `stepCountIs(8)` per turn plus per-message cleanup).

## Hardening milestone

- **Idempotent start:** in `startToolCall`, if `toolCallId` already exists in the entry, update its `toolName`/`status` instead of appending, so a duplicated `tool-call` part cannot inflate the count.
- **Settling without a start:** `settleToolCall` on an unknown `toolCallId` is a no-op. Add a single DEV `console.log` when this happens to catch provider-executed tool parts that never emit `tool-call`.
- **Truthful end states:** aborted turns keep the counts from the partial turn (they happened); turns that exhaust retries keep the last attempt's counts next to the error bubble. Add a one-line comment recording that choice in `use-chat.ts`.
- **Retry reset verified:** temporarily force a retry (`if (attempt === 0) throw new StreamIncompleteError("test")` after the first `tool-call` branch), confirm the count restarts at 1 instead of 2, then revert.
- **Failure status verified:** temporarily make `createFetchUrlTool` throw for one URL, confirm the row shows `Failed` in destructive color and the turn still completes, then revert.
- **Accessibility:** trigger is a real `<button>` with `aria-expanded`; decorative icons are `aria-hidden`; details use `ul`/`li`; no `aria-live` region on the count so a streaming turn does not spam screen readers. The count text alone carries the meaning.
- **Layout robustness:** long or unknown tool names truncate instead of widening the bubble; the row never exceeds the bubble's `max-w-[85%]`; with 8 calls the details list stays readable (scroll not needed, but check it does not push the composer off screen).
- **No persistence audit:** confirm by review that `src/lib/config.ts` gained no keys, `src/lib/turso-repository.ts` is untouched, and `Message` / `MessageModelInfo` are unchanged. No migration, no schema version bump.
- **Docs:** update `ARCHITECTURE.md` section 3 (transient `messageToolActivity` next to `conversationActivity`) and section 10 (tool-call counts are surfaced live from `fullStream`, session-only), and add the new component to the chat component list in section 7. Add TSDoc on every new exported declaration and type.

## Manual testing checklist

1. `npm run lint`, `npm run build` clean.
2. Settings > Tool: "URL fetching" enabled; no tool row in a plain `Say hello.` turn.
3. One-call turn: `Fetch https://example.com and tell me the title.` -> row shows `1 tool call`, spinner while running, spinner gone when settled, answer streams below.
4. Multi-call turn (two URLs in one prompt) -> count grows to `2 tool calls` within the same bubble.
5. Expand/collapse by mouse and by keyboard; verify focus ring, `aria-expanded`, and per-call `Done` labels.
6. Failure path (temporary throwing tool) -> `Failed` state visible, turn still completes, then revert the temporary change.
7. Retry path (temporary forced `StreamIncompleteError`) -> count restarts at 1 on the retry attempt, not 2, then revert.
8. Conversation switching while streaming: counts stay per bubble; the other conversation's bubble is unaffected.
9. Session-only: counts survive conversation navigation, disappear after reload, messages still load from Turso.
10. Theme check in light and dark; 8 sequential calls (repeat a fetch prompt) still renders compactly.
11. Lifecycle: regenerate, edit user message, delete message, delete conversation all remove the expected entries (temporary DEV counter log), then remove the log.

## Completion criteria

- The tool-call count renders inside the correct assistant bubble, live during streaming, and is absent for turns with no tool calls.
- The row expands to per-call names and statuses, collapsed by default, keyboard operable, readable in both themes.
- Counts are per assistant message, unaffected by other conversations streaming at the same time.
- Counts survive conversation switching within the session and vanish on reload.
- Nothing is written to Turso or `localStorage`; `messages` table, `saveMessage`, and `Message` are untouched; no migration added.
- Retries restart a message's count; message deletion, conversation deletion, regenerate, and edit remove the corresponding entries.
- All new declarations and types carry TSDoc; `ARCHITECTURE.md` reflects the transient slice and the new component.
- `npm run lint` and `npm run build` pass, and the manual checklist above is completed by the user.

## Quality check

- Observable result early: Milestone 1 ends with a visible live count in the bubble.
- Milestone 1 runs independently: store slice, stream wiring, and one component are enough to see it.
- Each milestone builds on a working flow: details (M2) and cleanup (M3) only extend the proven row.
- Runnable after every milestone: no milestone leaves a half-wired store or an unrendered slice.
- Architecture sufficient but not speculative: one slice module, five actions, one component, no interfaces for hypothetical variants.
- Cohesion and size: the oversized `src/store/chat.ts` gains four one-line cleanup calls instead of new state; transient state lives in the focused module created by plan 01.
- Declaration docs included with implementation; named contracts live in `chat-transient.types.ts`.
- UI added before infrastructure: no new settings, no persistence, no schema work.
- Safeguards after the main flow: dedupe, unknown-call handling, truncation, and accessibility come after the working row.
- Deferred work explicit per milestone; verification is manual and concrete, matching the project rule against writing tests.

# 01 - Conversation activity indicator

## Goal

Any conversation with an in-flight turn shows a spinner in place of its normal row icon (`MessageSquareIcon`, or `PinIcon` for pinned rows) in the sidebar, and the spinner disappears when that turn ends for any reason: success, provider error, user stop, compaction abort, or an unexpected throw. Because a running turn now outlives the component that started it, switching conversations no longer hides the fact that work is happening and no longer breaks the stop button for that conversation. The state is transient and in-memory only: never written to Turso, `localStorage`, or a persisted store slice.

## Assumptions and decisions

- Current state verified: `src/store/chat-transient.ts` and `chat-transient.types.ts` do not exist yet (`src/store` contains only `agents.ts`, `chat-helpers.ts`, `chat.ts`). This plan creates the transient module with the conversation-activity slice; the sibling tool-activity plan (02) extends the same files instead of creating a parallel store.
- One transient module, not two. Both concerns are per-turn ephemeral streaming state with identical teardown rules (cleared on turn end/delete, never persisted), so one slice module is the right home. A second store would duplicate the teardown rules and split ownership of the same lifecycle.
- `useChat()` is instantiated twice per chat page (`MessageList`, `MessageInput` in `src/components/chat/chat-area.tsx`), and `MessageInput` is keyed by `selectedConversation.id`, so it remounts on every conversation switch. Local `isGenerating` therefore cannot represent reality, and the second instance (`MessageList`) currently always reports `false`. The fix is one store-owned source of truth, derived per selected conversation.
- Keys are `conversationId`, not message id: a turn belongs to a conversation, and multiple conversations can be mid-turn at once because switching does not cancel the previous stream.
- Abort handles stay outside React state in a module-level `Map` inside the hooks layer (`src/hooks/chat-stream-lifecycle.ts`), not in the Zustand state. This keeps the store JSON-ish, prevents state churn on controller replacement, and keeps dependency direction store -> hooks out of the picture.
- Behavior change, deliberate: one `AbortController` per turn replaces the current per-attempt controllers in `streamAssistantResponse`. Today the loop replaces `abortControllerRef.current` with a fresh controller on attempt 0, silently orphaning the compaction controller, so pressing stop between compaction and the first attempt does nothing. One per-turn controller makes the registry exact and fixes that gap.
- Activity writes are phase-guarded (write only when something changed) so streaming deltas never touch the transient slice per token.
- Project rule: no unit/E2E tests. Verification is manual; a manual checklist replaces the automated testing milestone. `npm run build` (`tsc`) and `npm run lint` (`biome check`) are still run as correctness gates.
- `compactNow`'s `isCompacting` state and `compactAbortControllerRef` are untouched; manual compaction does not light the sidebar spinner (deferred).

## Proposed structure

```text
src/store/
  chat.ts                        (existing) compose the transient slice, clear activity on delete
  chat-transient.ts              (new) createChatTransientSlice: conversationActivity + setter
  chat-transient.types.ts        (new) ConversationActivity, ConversationActivityPhase, ChatTransientSlice
src/hooks/
  chat-stream-lifecycle.ts       (new) turn registry: start/phase/finish/abort + activity writes
  use-chat.ts                    (existing) owns the turn: begin in try, finish in finally, derive isGenerating
src/components/
  app-sidebar.tsx                (existing) ConversationActivityIcon, row icon swap, delete aborts
ARCHITECTURE.md                  (existing) transient slice + turn ownership notes
```

Responsibilities:

- `chat-transient.types.ts` holds only named contracts: `ConversationActivityPhase = "thinking" | "streaming" | "tool"`, `ConversationActivity = { startedAt: number; phase?: ConversationActivityPhase; toolName?: string }`, `ChatTransientSlice = { conversationActivity: Record<string, ConversationActivity>; setConversationActivity(conversationId, activity | null): void }`.
- `chat-transient.ts` holds the slice implementation only (no persistence, no side effects), matching the existing ephemeral precedent `messagesLoading: Set<string>` in `chat.ts` but isolated so stream-transient state has one home.
- `chat-stream-lifecycle.ts` is the only writer of turn activity, so "cleared on every exit path" is enforced in one place rather than scattered through `use-chat.ts`.
- `use-chat.ts` keeps orchestration only: it calls lifecycle functions and reads derived `isGenerating`.

## Milestone 1: Spinner that tells the truth

### Outcome

Send a message in conversation A: A's sidebar row swaps its icon for a spinner while the model thinks, streams, retries, and generates the title. The spinner clears on success, error, and stop. Switching to conversation B mid-turn keeps A's spinner visible, B's composer stays usable, and switching back to A shows the stop button again and stopping works. Two conversations can spin at the same time.

### Implementation

1. Create `src/store/chat-transient.types.ts` with the three documented contracts above. `startedAt` is epoch milliseconds. `phase` and `toolName` exist from the start but are only written in Milestone 2 so the type does not need a later migration.
2. Create `src/store/chat-transient.ts`:
   - `export function createChatTransientSlice(set)` returns `{ conversationActivity: {}, setConversationActivity }`.
   - `setConversationActivity(conversationId, activity)`: `null` deletes the key (no `undefined`/`null` entries in the record), otherwise stores the activity immutably. Type the `set` parameter structurally as `(updater: (state: ChatTransientSlice) => Partial<ChatTransientSlice>) => void` so the slice module needs no import from `chat.ts` and no runtime cycle is possible. TSDoc on the factory and the action.
3. `src/store/chat.ts`: add `import type { ChatTransientSlice } from "./chat-transient.types";`, change `export type ChatState = { ...existing } & ChatTransientSlice;`, and spread `...createChatTransientSlice(set)` first inside `create<ChatState>((set, get) => ({ ... }))`. In `deleteConversation`, call `get().setConversationActivity(id, null)` after the main `set` so a deleted conversation never leaves an activity entry behind.
4. Create `src/hooks/chat-stream-lifecycle.ts` with a documented module-level `Map<string, AbortController>` and four functions:
   - `startConversationTurn(conversationId): AbortController` aborts any controller already registered for that id (defensive), registers a new one, writes `{ startedAt: Date.now() }`, returns it.
   - `finishConversationTurn(conversationId, controller): void` deletes the registry entry and clears activity **only** when `activeTurns.get(conversationId) === controller`, so a superseded turn cannot clear a newer one's spinner.
   - `abortConversationTurn(conversationId): void` aborts the registered controller if present; it does not clear activity (the owning turn's `finally` does, keeping exactly one clearing path).
   - `updateConversationTurnPhase(conversationId, phase, toolName?)` is introduced here as a no-op-guarded stub used in Milestone 2: it returns early when the stored phase and tool name already match.
5. `src/hooks/use-chat.ts`:
   - Delete `const [isGenerating, setIsGenerating] = useState(false)` and `abortControllerRef`.
   - Derive, next to the existing `conversation` selector: `const conversationId = conversation?.id ?? null;` and `const isGenerating = useChatStore((state) => (conversationId ? Boolean(state.conversationActivity[conversationId]) : false));` (primitive return, no selector churn).
   - `stop`: `if (conversationId) { abortConversationTurn(conversationId); }`, dependency `[conversationId]`.
   - In `streamAssistantResponse`: after the `if (!activeProvider) return;` guard, `const turnController = startConversationTurn(conversationId);` then wrap the entire remaining body in `try { ... } finally { finishConversationTurn(conversationId, turnController); }`.
   - Remove every `setIsGenerating(true/false)` and every `abortControllerRef.current = ...` line, including inside the retry loop: delete the per-attempt `const abortController = new AbortController();` and use `turnController.signal` for both `streamText`'s `abortSignal` and the compaction signal (`const compactionSignal = turnController.signal;`). The two early `return`s (compaction abort, "Conversation too long to send") no longer reset anything; `finally` handles them.
   - Leave `runCompaction`, `compactNow`, `isCompacting`, `compactAbortControllerRef`, retry logic, and error handling untouched apart from the controller source.
6. `src/components/app-sidebar.tsx`:
   - Add a documented `ConversationActivityIcon({ conversationId, icon: FallbackIcon })` component above `AppSidebar`. It subscribes with `const activity = useChatStore((state) => state.conversationActivity[conversationId]);` and renders `<Loader2Icon className="size-4 animate-spin" role="img" aria-label={activityLabel(activity)} />` when active, otherwise `<FallbackIcon className="size-4" />`. Label defaults to `"Generating response"`; Milestone 2 refines it per phase.
   - In `renderConversationItem`, replace `<Icon className="size-4" />` in both the rename row and the `SidebarMenuButton` row with `<ConversationActivityIcon conversationId={conversation.id} icon={Icon} />`. Keep the existing `{ icon } = { icon: MessageSquareIcon }` signature so pinned rows still pass `PinIcon`.
   - Do not touch the hover action container, `className="pr-14"`, `tooltip={conversation.title}`, or `group-data-[collapsible=icon]:hidden` on the actions, so rename/delete stay usable and the icon-only sidebar still shows the spinner.

### Verification

1. `npm run lint` and `npm run build` pass.
2. `npm run tauri dev`, open a conversation with a configured provider, send a prompt with a long answer. Observe the row icon become a spinner immediately (before the first token, including during auto-compaction) and revert to `MessageSquareIcon` when the turn ends.
3. Pin that conversation, send again: the spinner replaces `PinIcon` during the turn and the pin comes back afterwards.
4. Start a turn, click a different conversation in the sidebar, then click back: the first row keeps spinning while you are away, and on return the composer shows the stop button; press it and confirm the spinner clears and the partial answer stays.
5. Start a turn in A, immediately send in B: both rows spin simultaneously; each clears on its own.
6. Force a failure (disable network or set a bad base URL): the spinner clears and the error bubble/toast appears.
7. Collapse the sidebar to icon mode: the spinner is visible in the active row and the hover rename/delete actions stay reachable in expanded mode.
8. Confirm no spinner appears for conversations that never started a turn and that a page reload shows no spinner anywhere (nothing persisted).

### Deliberately deferred

- Phase-specific labels (thinking/streaming/tool) and tool names in the accessible label.
- Aborting a stream when its conversation is deleted.
- Any spinner for manual `compactNow` (`isCompacting`).
- Sidebar re-render cost: `AppSidebar` still re-renders per token because it maps the `conversations` array; this milestone must not make that worse, and memoizing rows is a separate change.
- Reduced-motion handling for the spinner.

## Milestone 2: Accurate stage and clean teardown

### Outcome

The spinner's accessible label says what the turn is actually doing ("Thinking", "Generating response", "Using web search"), and deleting a conversation mid-turn stops that stream instead of letting it run invisibly.

### Implementation

1. `src/hooks/use-chat.ts`: in the `for await (const part of stream)` loop, add phase updates outside the development-only logging block so production builds track them too:
   - `reasoning-delta` -> `updateConversationTurnPhase(conversationId, "thinking")`.
   - `text-delta` -> `updateConversationTurnPhase(conversationId, "streaming")`.
   - `tool-call` -> `updateConversationTurnPhase(conversationId, "tool", part.toolName)`.
   - `tool-result` and `tool-error` -> `updateConversationTurnPhase(conversationId, "streaming")`.
   Keep the existing `if (import.meta.env.DEV)` logging branches intact; restructure the `else` chain only as much as needed so tool parts are handled once. The equality guard in `updateConversationTurnPhase` guarantees text deltas do not write to the store.
2. `src/hooks/chat-stream-lifecycle.ts`: finalize `updateConversationTurnPhase` to preserve the existing `startedAt` and to clear `toolName` when the phase leaves `"tool"`.
3. `src/components/app-sidebar.tsx`: extend the label helper so `phase === "tool"` renders `Using ${toolName}`, `phase === "thinking"` renders `Thinking`, everything else renders `Generating response`. The glyph stays `Loader2Icon` with `animate-spin` for every phase.
4. `src/components/app-sidebar.tsx`: in `handleDeleteConfirm`, call `abortConversationTurn(deleteTarget.id)` before `deleteConversation(deleteTarget.id)`. `chat.ts` already clears the activity entry, and the stream's `finally` will find no registry entry to clean.

### Verification

1. `npm run lint` and `npm run build` pass.
2. Send a prompt with a reasoning model at `low`/`medium` thinking: inspect the row via devtools (or hover the collapsed-sidebar tooltip) and confirm the accessible label transitions from `Thinking` to `Generating response` without the spinner ever disappearing between phases.
3. Enable a tool (e.g. web search) and ask something that triggers it: during the tool call the label reads `Using <toolName>`, then returns to `Generating response`.
4. With React DevTools "highlight updates" or the Profiler, record a token stream: the sidebar row must not re-render more often than before this change (phase writes happen only a handful of times per turn).
5. Start a long turn, delete that conversation from the sidebar: the row disappears, the network/proxy activity stops promptly, and no console error is thrown. Confirm no lingering `conversationActivity` entry by checking that a newly created conversation with the same row position shows no spinner.
6. Regression sweep: send, stop, error, switch away/back, two concurrent conversations. The spinner behaviour from Milestone 1 is unchanged.

### Deliberately deferred

- Per-phase glyphs or tool icons in the row.
- Turn duration display from `startedAt`.
- Spinner for manual compaction.
- Restoring activity after a window reload (explicitly wrong; activity is transient).

## Hardening milestone

- Audit every exit path in `streamAssistantResponse` and confirm the single `finally` clears activity: missing provider guard (before `start`), compaction abort, compaction failure with "too long to send", all retry attempts exhausted, provider error, user abort, unexpected throw from `addMessage`/store writes, title-generation failure (already caught internally). Verify by reading the final function top to bottom and listing each `return`/`throw`.
- Confirm the identity guard in `finishConversationTurn` and the abort-existing behaviour in `startConversationTurn` prevent a stale turn from clearing a newer turn's spinner, and that a leaked `conversationActivity` entry can never lock a composer permanently (`isGenerating` disables the textarea and shows stop, so a leak would be user-visible; the single `finally` is the guarantee).
- Confirm no new module writes activity anywhere except `chat-stream-lifecycle.ts`, and that nothing in the transient slice or lifecycle module touches `localStorage`, `saveConversation`, `saveMessage`, or `persistConversation`.
- Accessibility: spinner has `role="img"` and a changing `aria-label`; the row keeps `tooltip={conversation.title}` when idle; collapsed mode, rename mode, and pinned rows all render the correct icon state.
- Re-check `src/hooks/use-chat.ts` size: the turn wrapper should be a small diff around existing code, with the registry and activity logic extracted to `chat-stream-lifecycle.ts` rather than added inline. Do not restructure streaming behavior beyond the controller source.
- Documentation: update `ARCHITECTURE.md` section 3 (`useChatStore` state list) with the transient slice and section 4 with a bullet stating that turn activity and abort ownership live outside component instances (`conversationActivity` in memory only, controller registry in `hooks/chat-stream-lifecycle.ts`); add `hooks/chat-stream-lifecycle.ts` to the section 7 module list. Add TSDoc for every new named function and the new component.
- Run `npm run lint` and `npm run build`; fix any reported issue rather than suppressing it.
- Explicitly out of scope but recorded: `CHANGELOG.md` entries carry commit hashes and are written at release time.

## Manual testing checklist

1. Send a prompt in a single conversation: spinner replaces the message icon immediately and clears only when the answer completes.
2. Long reasoning phase with thinking enabled: the spinner is visible throughout, and the label shows `Thinking`.
3. Tool-using prompt: the label shows `Using <toolName>` during the call and returns to `Generating response`.
4. Provider/network error: spinner clears, error bubble and toast appear.
5. Press stop (button and Escape): spinner clears, partial output is kept, composer returns to send mode.
6. Switch to another conversation mid-turn and back: spinner persists, stop works on return, the textarea is disabled only in the streaming conversation.
7. Two conversations streaming at once: both rows spin, each clears independently.
8. Pinned conversation: spinner replaces `PinIcon`, then `PinIcon` returns.
9. Collapsed sidebar: spinner is visible; expanded sidebar hover rename and delete still work; rename input row still shows the spinner while the turn runs.
10. Delete a conversation mid-turn: stream stops, no residual spinner, no console errors.
11. Reload the app mid-turn: no spinner anywhere (nothing persisted), and the composer is usable.
12. `npm run lint` and `npm run build` pass with no new warnings.

## Completion criteria

- Every in-flight turn shows a spinner on exactly its own conversation row, and the spinner disappears on success, error, user stop, compaction abort, delete, and unexpected failure.
- Stop works for the active conversation after switching away and back, and the composer's generating state matches the row indicator.
- Multiple simultaneous turns are represented correctly, and deleting a conversation ends its stream.
- No transient activity is persisted, and no code path other than `chat-stream-lifecycle.ts` writes it.
- Hover rename/delete, pinned rows, rename mode, and collapsed mode all behave as before apart from the icon swap.
- `ARCHITECTURE.md` reflects the transient slice and turn ownership; `npm run lint` and `npm run build` pass; the manual checklist above passes.
